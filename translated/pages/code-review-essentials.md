## 软件团队代码评审要点

2015 年 2 月 9 日

代码评审是任何协作型软件项目的重要组成部分。大型软件系统通常由不止一个人编写，因此一个高效运转的软件团队需要一套稳健的流程，让团队成员以及代码库本身都朝着正确的方向前进。

代码评审是一个强大的工具，它能够：

- 帮助团队成员在系统变化时调整他们对系统的心智模型

- 确保变更能够正确地解决问题

- 开启关于设计优缺点的讨论

- 在缺陷进入生产环境之前将其捕获

- 保持代码风格和组织结构的一致性

把这些好处看作一种需求层次会很有帮助。

[图：代码评审：需求层次]

## 让团队成员保持一致

代码评审最关键的作用，是让团队中的每一位成员都朝着正确的方向前进。你无法安全地修改一个自己不了解的系统，因此代码评审能让团队在认知上保持一致。当 Bob 为账务子系统提交一个拉取请求（PR）时，Amy 在评审 Bob 的代码的过程中，会同步更新她对那个系统的心智模型。Amy 有机会就自己不理解的部分提出问题，而 Bob 则能通过澄清自己的设计决策、并向他人讲解自己的工作而受益。当 Amy 一个月后需要修改账务子系统时，她对系统的心智模型早已是最新的、随时可以投入行动。她花在阅读代码、在大脑里拼凑系统全貌上的时间更少，而花在思考更高层抽象与设计上的时间更多。每个人都是赢家，因为每个人都在保持一致。

## 做好一个拉取请求

在你动笔写下任何一行修改系统的代码之前，先问问自己下面这些问题：

- "我做的这件事是对的吗？" 客户、团队内部成员以及其他各方总会存在相互竞争的需求。在你深入投入之前，这是理清优先级的好办法。诸如迭代 / 冲刺规划会议等其他流程也有助于让这件事保持在正轨上。

- "团队是否已经一致认同这个变更就是正确的？" 如果没有，最好先通过邮件、或者当面展开一次设计讨论。当人们在变更之前就设计达成一致时，你的变更就更有可能被接受。

- "我怎样才能把这个变更拆分成易于评审、易于理解的、可消化的块？" 小变更更容易思考和理解。当团队能够快速领会你的变更时，良好的讨论才会随之而来。如果你的变更过于庞大，队友们会看得两眼发直，最终你得到的可能只是几条风格上的吹毛求疵。

- "我打算如何测试这个变更，以消除缺陷并确保正确性？" 你们或许有 QA 部门，但交付高质量、可正常工作的软件仍然是开发者的职责。易于测试的软件通常耦合度更低、被拆分成更小的块，也更容易推理。你需要为所有变更都准备一份测试计划。

我发现，提前回答这些问题，从长远来看帮我省去了大量头疼。你最不想做的就是花好几天写出一个变更，结果却因为根本性的设计缺陷或团队分歧而被否决；或者因为没有人能验证其正确性，你的变更被卡住。再说一次，目标是在修改系统的同时，让其他团队成员始终了解你的变更进展。问问自己打算如何把工作拆分成一口大小的块、以及如何测试这些块，在很多方面都很有帮助：

- 它能降低风险

- 它让变更更容易推理

- 它推动你走向更好的设计

你宁可拿手术刀做许多次小而精准的切割，也不愿用砍刀砍出一条巨大的伤口。在大多数增量式场景下，我更倾向于用手术刀驱动的开发方式，而喜欢把砍刀留到需要删除大块死代码的时候。

## 发送拉取请求

好了，你已经取得了团队的认可，确认你的变更是好的，也实现了你当初想要构建的设计。那么，实际发送拉取请求最高效的方式是什么？你在自己的变更上付出了很多努力，你希望团队里的其他成员关注你的拉取请求并给出快速反馈。你该怎么做呢？

还记得我前面说过的吗——代码评审最重要的部分，是让团队整体的心智模型保持一致？你的其他队友很可能在做与你完全不同的事情，也许在系统中完全不同的部分。他们的大脑处于完全不同的上下文之中，所以你必须通过提供他们评审所需的有益指导来克服这一点。这意味着要写一份条理清晰的描述，说明你做了哪些变更、为什么做这些变更，以及任何他们仅靠阅读代码无法获知的相关信息。不要让你的队友做超出必要的心智劳动。

我们来看看几个拉取请求描述的好例子和坏例子：

坏例子：

```
标题：修复未初始化内存缺陷
描述：

这就是之前 Bob 和我讨论的那个缺陷。我在编译器上遇到了麻烦，
但还是设法把它弄好了。想听听大家的意见。

```

如果你是这个拉取请求的开发者，请停下来，设身处地地站在代码评审者的角度想一想。标题含糊不清，引发的问题比回答的还多：内存缺陷在哪里？这个变更有多关键？之前你和 Bob 讨论的到底是什么缺陷？你在编译器上遇到了什么麻烦？这段描述既没有提供关于问题的任何有用上下文，也没有提供关于你所做变更的任何有用说明。如果这个拉取请求很长，评审者就不得不一头扎进代码里，费尽心思去推断上下文，甚至还没有机会思考这个变更如何融入系统的连贯设计。

下面是一个改进后的例子，它有助于让变更集更清晰：

```
标题：修复因未初始化内存导致的进程启动崩溃 [#54633]
描述：

这个缺陷是由于我们统计用的 Counter 类中的内存初始化错误，导致进程在启动时崩溃。
我和 Bob 讨论过这件事，我们都认为这些崩溃是一个罕见的边界情况，
不值得发布一个紧急修复（hot-fix）版本。下面是变更的摘要：

- 将底层 int 变量移入类初始化器中，以防止 Counter 中出现未初始化的内存。
- 重构了 Counter 接口，以简化调用方的条件逻辑，并防止进一步的差一（off-by-one）计数问题。
- 添加了一个能够暴露该崩溃的单元测试。

测试：我已确认测试套件仍然通过，并手动确认了本地不再发生该崩溃。

```

这个拉取请求描述里有几点得到了改进：标题的描述性足够强，能够给评审者一些简短上下文，并吸引他们点开邮件了解更多。评审者知道这是一个进程崩溃（这通常是非常糟糕的事情），而且还有一个缺陷报告编号，如果评审者有兴趣更深入地了解这个问题，就可以去阅读缺陷报告的更多细节。新描述还概述了问题发生的位置，并帮助提供了关于这个修复有多关键的上下文。此外还有一个摘要，列出了拉取请求中的高层结构性变更，让评审者在查看代码之前就能对变更形成一幅心智图景。代码评审者不应该对自己发现的东西感到意外。这个例子还概述了所执行的测试，这将让评审者对变更经过深思熟虑、经过充分测试、可以合并抱有信心。让你的评审者轻松成功——让他们点击 "merge"（合并）变得简单到极点。

## 评审者：给出建设性反馈

评审流程中接下来要考虑的部分，是向你的同事给出建设性反馈。如果目标是清晰和一致，那么给出高质量的、建设性的反馈，就能帮助每个人更好地理解系统，并推动代码变得更好。

避免说这样的话：

- "这个设计是坏的。" 它为什么是坏的？怎样才能让它变得更好？这样的说法会伤害信心，还可能挫伤自尊。

- "我不喜欢这个变更。" 你为什么不喜欢它？你希望改成什么样？不喜欢某样东西是可以的，但你应该把自己的想法表达清楚，并提供关于如何改进代码的有用线索。

- "你能不能把它重写得再清楚一点？" 我现在的写法有什么问题？我该怎么重写？哪里不清楚？这样的评论本身就不清楚，也没有给出一条简单的出路。

相反，可以说这样的话：

- "这段代码如何处理负整数？" 这种反馈很具体，能促使开发者自己去思考各种结果。作为评审者，你可能知道这段代码遇到负整数会崩溃，但最好还是让开发者自己悟出来。这样的问题也可能暗示着存在测试缺口，或者需要进一步明确范围规范。

- "这部分让我很困惑，我不明白为什么 A 类在和 B 类通信。" 如果开发者没有提供有用的描述，代码结构也不够整洁，那么这种评论就有助于推动设计更清晰、代码更干净。

- "看起来你在这里打破了一个接口边界。这会对用户产生什么影响？" 你指出了自己注意到的问题，同时善意地假定他们是有意为之。现在他们可以仔细思考打破接口边界所带来的那些看不见的后果，然后要么为自己的决定给出理由，要么选择改变它。

总的来说，把反馈包装成问题是推动清晰度和正确性的好办法，同时还能帮助开发者在未来改进他们的设计。高质量创意写作小组通常就是这样互相给反馈的。在创意写作的场景下，说"我不喜欢这个角色"这类话是有害的；而同样的评论可以被重新表述得更清晰："在第一章里，你的角色既温暖又富有同情心，而现在他却变得冷漠又冰冷。在我看来，他不像个真实的人。" 现在就有了具体的反馈，可以据此进一步澄清、找出问题所在。

程序员喜欢解决问题、指出毛病，所以他们天生就喜欢发现并指出缺陷。把代码评审当作一种通过找出同事代码里的问题来证明自己有多聪明的方式，这很有诱惑力。不要这样做。代码评审是一种让更多双眼睛关注一个变更、找出关键问题的方式，但你的目标应该是：以鼓励团队成员提升技能的方式来评审，同时解决眼前的问题。

## 关于风格要点

花括号位置、变量 / 函数命名、缩进和空格等问题应该得到处理，但它们并不是优秀代码评审的核心目的（注意，我把它们放在了代码评审金字塔的顶端）。如果你发现团队把 90% 的时间都花在缩进和变量命名上吹毛求疵，那么你很可能是在把大家的时间浪费在那些大多可以自动化的事情上。写一份风格指南，在签入（check-in）时强制执行缩进和空格规范，然后把时间花在聚焦更高价值的问题上。我并不是要贬低风格一致的重要性。恰恰相反，拥有一套一致的惯用风格，是让代码库易于阅读和理解的最简单方法之一。不过，如果你把所有的代码评审都花在这些简单任务上，那就问问自己，是不是在回避那项更困难、也更重要的工作——让团队在认知上保持一致、思考更高层的设计。
