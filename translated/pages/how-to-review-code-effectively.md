## 什么样的代码评审是好的或坏的？

好的代码评审能增加清晰度，并推动代码走向比初始状态更好的状态。

作为评审者，沟通的清晰度是关键。你要明确哪些评论属于个人偏好，哪些是阻碍批准的拦路项。给出你建议的做法的示例，可以让你的代码评审更有分量，也让你要表达的意思更清晰。如果你能提供来自与 PR 相同仓库的示例，那就更好了——这通过鼓励一致的实现方式进一步支持了你的建议。

相比之下，糟糕的代码评审缺乏清晰度。例如，不带任何评论的一刀切式批准或驳回，会让 PR 作者怀疑评审是否认真彻底。即使只是在批准时复述一下你对 PR 作者意图的理解，也能揭示你和作者是否拥有相同的理解。

一份没有说清楚建议应在何时落实的代码评审，对作者来说也可能是糟糕的体验。指出现有未改动的代码应当重构、或某个额外情况应当处理，这都没问题，但重要的是要说明这些是否是批准的前置条件。如果这个 PR 即使不采纳你的建议也可以合入，务必说清楚。保持较小的改动量、把那些改动作为单独的 PR 单独发布，可能会更稳妥。

下面是一条体现了明确性、并清晰传达了建议实现方式的代码评审评论：

“我看到你的新方法和这个文件中现有的风格一致，接收 [X] 个参数。参数这么多会损害可读性，也暗示这个函数做了太多事情。你觉得在之后的 PR 里把这个方法和现有的方法一起重构、减少它们的参数数量怎么样？”

这条评论做得好的地方：

- 提供了具体的细节。

- 引用了具体的代码或议题。

- 对问题给出了解决方案建议。

- 引用了证据或给出了解释

在光谱的另一端，这里有一些本可以写得更好的评审评论示例：

“我不喜欢这个。”——评审者不喜欢的是什么？他们心里有没有可以明确说出来的替代方案？

可能的改进：

- “这一行做的事情太多了，我们能不能简化它以提升可读性？”

- “我觉得这里会有性能问题，因为存在 n+1 查询。”

- “这里我们能不能用 [首选框架] 提供的解决方案，而不是自己写一套定制实现？”

“这样不行。”——为什么这些改动行不通？

可能的改进：

- “这样不行是因为 [X]，请参见这个相关议题：[议题链接]。”

- “之前在 [拉取请求链接] 里试过这种做法，因为 [X] 没能成功。”

- “如果你在 [X] 上遇到问题，可以试试 [替代方案]。”

“我觉得这修复了一个 bug。”——我很喜欢你的提醒，但是否还有任何额外的上下文（比如议题链接）能让这一点更清楚？

可能的改进：

- “我觉得这修复了 [议题链接]。”

- “这是在修复 [议题链接] 里的那个 bug 吗？”

- “这看起来像我们遇到过的那个 bug，参见 [构建失败的链接]。谢谢你的修复！”

## 如何给出好的代码评审

### 提出疑问

我把 PR 作者视为对 PR 所做改动最了解上下文的人。我可以根据我的过往经历——我在 Ruby on Rails 单体应用、TypeScript 或流量很大的数据库方面的经验——指出我看到的问题，但我相信作者对我所提问题的回答。我认为他们对具体细节的理解比我更好。

提示

如果你刚接触一个代码库或团队，可以在代码评审中提问，以了解技术栈以及有哪些内部工具和库可用。你评审的每一个 PR 都是一次机会，可以弄清作者为什么更倾向于某一种做法而非另一种。

我也很喜欢问一些涉及代码中所做假设的问题。他们处理的数据是什么样的结构（shape）？是否存在不符合该结构的数据？代码对此能否很好地应对？代码是否资源密集？它的性能会好吗？作为评审者，我最喜欢的回应是作者提供一个自动化测试，来验证这些场景下的行为。我第二喜欢的回应是经验数据，比如来自我们数据仓库的一条查询，或一张 Datadog 图表，用来说明为什么这些场景不是问题。

作为 PR 作者，我喜欢收到问题。当有人提出问题时，就给了我空间去解释为什么我对自己的改动有信心，并根据需要引用议题、查询或图表。这也让我能够与他人分享我的知识和经验。看到我回复的不仅有作者，还有其他评审者，以及未来可能追查某个过往决策上下文的读者。

### 给予肯定

除了提问之外，对你认同的 PR 部分发表评论也是很好的做法。这些评论可以表明你阅读并理解了改动的内容，或者表明你验证了代码中的某个假设。这里有几个例子：

- “这看起来和这个模块里其他类使用的模式一致。”

- “谢谢你为此添加了测试！”

- “这比以前可读性好多了。”

以我的经验，收到这样的评论也让人感觉很好。接受代码评审有时会让人筋疲力尽。当我要应付来自多方的提问和建议时，收到几条不对我提出任何要求、而是支持和认可我已付出努力的评论，会是很好的激励。

### 警惕偏见与假设

很容易让你的评审受到你对评审者、或对他们所改代码区域的偏见影响。你习惯了某人在某个领域工作、或拥有一定的资历，就假定他们知道自己在做什么——但每个人都会犯错。你对他们的改动所投注的目光、你检验他们假设或验证自己假设的提问，都能在问题部署上线之前将其发现。

我很推崇写测试，因为测试能消除一部分偏见。当你写一个测试来验证代码是否正常工作时，你不必听作者的一面之词，只需看看测试是否通过——当然前提是你把测试写对了。😅

我也很推崇初级开发者在代码评审中向高级开发者提问，即使他们认为自己的问题很傻、或答案显而易见。如果对你来说不明显，那就是有效的。对其他人来说也不会是显而易见的！把问题提出来，给作者写下答案的空间，把这点教育价值留给后来的人。

### 是否批准

我把自己的评审视为一道阻塞关卡，它可以阻止另一个人改进我们的产品，所以我会审慎地保留批准。我常常会有个人偏好，并建议一些我希望作者做出的可选改动，但我不会仅仅因为那些偏好就扣住批准。如果我对某人的 PR 有建议，但这个 PR 按现状合入不会破坏生产环境、不会对用户产生负面影响、也不会以其他方式引发问题，我就会连同这些评论一起批准。作者可以选择在合并 PR 之前处理我的反馈，也可以在另一个分支里跟进。

提示

使用特性开关，并让你的 PR 保持小巧。你的改动越不可怕，它在生产环境中就能越快被回滚，我也就越容易批准它！

在评审代码时，要牢记你建议的重要性。为了落实你的建议而推迟发布值得吗？值得让作者走完「看到你的反馈、做出建议的改动、等待 CI、复审、部署、最终合并」这整个循环吗？如果缺少某条建议并不会让某人的日子更难过，那就让作者决定是否或何时做出建议的改动。

「请求更改（Request changes）」选项会阻止一个 PR 被合并，直到评审者回来批准它。我很少使用它，因为它通常感觉过于强硬。我相信我的团队知道何时该批准一个 PR，所以队友的批准可以替代我的。同样，我相信 PR 作者会尊重并考虑我的反馈，而不是因为别人批准了而我没有，就盲目合并。我唯一会选「请求更改」的情况，大概就是我认为存在一个紧急的安全问题，并且担心他们在合并前看不到我的顾虑。

为什么在使用 AI 编码工具时代码评审很重要

AI 编码工具通常包含各种防止不正确或不安全代码的防护措施，但不要被麻痹而产生虚假的安全感。作为掌舵的人类评审者，你是最后一道防线，应该以同等的勤勉程度评审所有代码。

## 如何从代码评审中获得最大收益

### 评审你自己的代码

GitHub 高级软件工程师 Paul Smith 教会我在请别人评审之前先评审自己的 PR，我也建议你这么做。先过一遍，在那些非显而易见的改动上、或在那些你如果在别人的 PR 里看到就会提问的地方，留下行内评论。自评审还可以帮助判断一个 PR 是否过大、是否值得拆分。

特别致谢：如果你在意保持 PR 小巧，可以使用 lerebear/sizeup-action 自动给 PR 打上标签，标明其复杂度和规模。

### 欢迎合并后的评审

如果我在有人来得及评审之前就合并了一个 PR，我依然欢迎他们的评审。如果我的 PR 弄坏了什么东西或产生了意料之外的后果，在 PR 上就此留下评论，会留下一条面包屑轨迹，帮助未来的读者追查发生了什么！

如果我在已合并的 PR 上收到评审，我会像 PR 合入之前一样处理这些反馈。也许会是一条解释我观点的评论，也许是几个额外的 PR 来对我最初发布的代码进行迭代。也许是开一些新的议题来记录还需要完成的额外工作。

### 使用草稿拉取请求

当你创建一个新的 PR 时，可以选择把它设为草稿。我非常依赖草稿阶段来表明我是否想要评审。例如，如果某个必需的 CI 构建在失败，或者我还没做完，我就会保持草稿状态。我也倾向于对别人的 PR 抱有同样的预期：如果它是草稿，我就假定作者还没准备好接受评审。如果它被标记为「已准备好评审」，我就假定阻止他们部署这个 PR 的，只剩获得足够的批准这一件事。

草稿状态意味着 PR 还没完成，所以在解决合并冲突或处理评审者反馈时，我会把 PR 移回草稿。如果我必须修改代码，我会先把 PR 标记为草稿，以免让已经评审过的人不堪重负。当我把它移回「就绪（ready）」时，会向那些评审者发送一条 GitHub 通知，让他们可以再看一遍。

### 保持谦和

我想起了那句俗语「蜂蜜比醋能捉到更多苍蝇」。我希望自己的 PR 得到评审，所以我喜欢回复自己 PR 上的评论——尤其是当我不同意评审者的意见时。即使我不给评审评论写回复，我也常常会用一个 👍 来表示同意，或用一个 ❤ 来表达感谢。

我希望评审者相信他们的建议不会被遗忘，所以我会通过评论让他们了解进展。如果我同意他们的建议——例如进一步重构现有代码——我可能会在表示同意的同时，也反对在当前这个 PR 里做这个改动。当我在之后的 PR 里落实了他们的反馈时，我会回来附上链接，让评审者知道他们的反馈没有被忽视。

我也会在后续落实了建议改动的 PR 里 @ 他们，并附上一句说明「这个 PR 落实了 @某某 在 <上一个 PR URL> 中的反馈。」这既为其他读者提供了上下文，也向最初的评审者致意，把功劳归于这个想法的提出者。

当你信守承诺、在后续分支中落实反馈时，这有助于与评审者建立信任，从而让他们安心地批准你未来的 PR，因为他们知道你不会把事情半途而废。

## 总结

代码评审对产品质量的重要性无论怎样强调都不为过，尤其是在 AI 代码生成的时代。在我的职业生涯中，很多次仅仅因为多了一双眼睛，就发现了一个 bug 或避免了一次事故。代码评审非常值得投入时间，无论是花在日常评审、理顺流程，还是构建支持它的自动化上。对开发者来说，现在彻底评审 PR 比之后处理一个已经发布到生产环境的问题要更快、也更省心。

感谢你对代码质量的这份用心，愿意读我关于代码评审的理念。你最近查看过你的评审队列了吗？也许现在正是把这些想法付诸行动的好时机。

如果你想进一步了解如何在 GitHub 上使用 PR 评审，可以看看 GitHub Community 上由资深 DevOps 架构师 Mickey Gousset 和资深 DevOps 架构师 Joshua Johanning 撰写的文章，讨论「评审拉取请求的 5 个技巧（5 Tips for Reviewing a Pull Request）」。
