# 使用 Claude Code 与 OpenAI Codex 挖掘现代 Web 应用中的漏洞

我们对 AI 编程智能体挖掘漏洞能力的深入探究，揭示了出人意料的长处、关键短板，以及一个严重的稳定性问题。

TL;DR：我们评估了 AI 编程智能体在真实代码中发现漏洞的效果。

- 

如何评测：我们让 Anthropic 的 Claude Code（v1.0.32、Sonnet 4）和 OpenAI Codex（v0.2.0、o4-mini）在 11 个流行且规模庞大的开源 Python Web 应用中寻找漏洞。它们合计产出了 400 多条安全发现，由我们的安全研究团队逐一评审。

- 

AI 编程智能体能发现真实漏洞：Claude Code 发现了 46 个漏洞（14% 真阳性率——TPR，86% 假阳性率——FPR），Codex 报告了 21 个漏洞（18% TPR，82% FPR）。其中约有 20 个属于高危漏洞。

- 

AI 能理解上下文，却卡在数据流上：Claude Code 最擅长发现越权对象引用（IDOR）缺陷，真阳性率（TPR）为 22%（13 个正确问题/59 个报告），但在跨多个文件与函数进行污点追踪时表现挣扎，SQL 注入的 TPR 为 5%（2/38），XSS 的 TPR 为 16%（12/74）。

OpenAI Codex 则很难报告出任何正确的 IDOR，TPR 为 0%（0/5），在 SQL 注入（0%，0/5）和 XSS（0%，0/28）上表现极差，但出人意料的是，它在路径遍历上报告的正确答案比 Claude Code 更多，TPR 为 47%（8/17）。

- 

非确定性是一大难题：在完全相同的代码库上多次运行完全相同的提示词，结果常常大相径庭。在某个应用中，三次相同的运行分别产生了 3 条、6 条，随后是 11 条不同的发现。

关键要点：

- 

配备相对简单的、以安全为目标的提示词，AI 编程智能体已经能够在真实应用中发现真实漏洞。

- 

但是：视漏洞类别而定，结果可能相当嘈杂（假阳性率高），尤其是在传统的注入类漏洞上，如 SQL 注入、XSS 和 SSRF。

- 

详细的评测与基准测试，对于理解某种方法在发现漏洞方面的有效性至关重要（这一点历来如此，但在面对 LLM 这类非确定性工具时更是如此），也能让你了解你的改进是否走在正确的方向上。

## 引言

在 Semgrep，我们每天都与应用程序安全（AppSec）打交道。长期以来，我们一直在产品中将 AI 投入生产（Assistant 背后的技术、用于测试我们 AI 工作流的 promptfoo、使用安全研究人员的分级来评估自动分级性能），不断研究如何将传统、确定性的分析与现代 AI 的上下文能力最优地结合起来，而不盲目追逐潮流。

这项研究正是这一持续使命的一部分。我们正着手开展一次深入、公开的探索，以回答一个萦绕在每个人心头的问题：LLM 在源代码中发现漏洞的实际效果到底如何？

## 关于基于 AI 的漏洞挖掘的开放性研究问题

为了指导我们的研究，我们将“LLM 是否擅长找 bug？”这个宽泛的问题，拆解为更具体、可衡量的子问题。

- 

基于 LLM 的漏洞挖掘的假阳性率和假阴性率是多少？它是否会因编程语言、框架、代码库规模或漏洞类别而有所不同？它对代码的编写方式有多敏感？

- 

造成假阳性和假阴性的常见原因有哪些？

- 

这种分析有多确定性？每次都能得到相同的结果吗？

具体到注入类漏洞，我们还想了解：

- 

LLM 在追踪 source（如用户提供的值）与 sink（如消费原始 SQL 查询的方法）之间的用户输入时效果如何？

- 

它能跨函数、跨文件追踪数据吗？

- 

它能对净化函数及其他安全控制进行推理吗？

- 

它能对来自第三方开源依赖的函数进行推理吗？

## 常见 SAST 基准测试的问题：缺乏真实性

在深入探讨我们的发现之前，先谈谈我们如何衡量 AI 的性能。目前大量的研究/结论所依赖的基准测试虽然有价值，却无法充分捕捉真实世界代码的复杂性。

- 

带有已知漏洞的应用：这些基准测试只使用带有已知漏洞的开源应用；多亏 Kinnaird McQuade，其中许多可以在 vulnerable-apps 中找到。如果你读过本博客，或许能认出其中一些名字：WebGoat、JuiceShop、OWASP Benchmark 等等。但这里存在一个问题：当前的 LLM 很可能已经“消化”了这些仓库的代码，以及互联网上大量公开的解析文章，这赋予了它们先验知识，从而使结果产生偏差。

它们的代码往往并不真实，充斥着大量注释、标注和变量名，这些内容或暗示、或直接描述了漏洞所在的位置以及如何利用它们。有时，工具的结果甚至被直接提交到了仓库中。

[图: /assets/blog/2025/09/javascriptvulny.png]来自 javaspringvulny 的 SearchService.java

[图: /assets/blog/2025/09/juiceshop.png]来自 juiceshop，该挑战就写在文件名里……

- 

XBOW 提供了面向自动渗透测试工具的基准测试，但不适用于静态分析：这些代码往往过于刻意和简化，无法代表真实应用。ZeroPath 在对其做净化时做得不错，但只有一小部分被净化了。此外，这些测试用例中的每一个都是极小的应用，旨在刺激某个专门的攻击场景。如果聚焦于 Python 基准测试，XBOW 有 45 个；45 个各不相同的小应用，平均不到 98 行代码、3 个 Python 文件。这个规模太小了，无法体现跨整个代码库或多个函数进行搜索与推理的复杂性。

- 

CVE 记忆偏差：LLM 是在互联网海量公开数据（包括那些 CVE 被发现并修复的代码库本身）上训练出来的。这造成了一个根本性的数据污染问题。AI 可能并非通过新颖的分析检测出漏洞，而只是识别出了它在训练期间记忆的模式。

更近期，学术界设计了诸如 CyberGym、Eyeballvul 或 SecVulEval 之类的基准测试。这些测试展现了巨大的进步，更接近真实世界的例子，但它们要么缺乏对现代 Web 应用的关注，要么将漏洞从更广泛的应用上下文中剥离出来。

- 

EyeballVul：一个较新的基准测试，来自 Timothée Chauvin，它从开源项目中提取真实的、经人工审查的漏洞，并将其呈现为最小、可复现的测试用例。虽然基于真实代码，但它仍将漏洞从更广泛的应用上下文中剥离出来，使得搜索问题变得更容易。

- 

SecVulEval 与 CyberGym：这些套件旨在评估 C 或 C++ 中的漏洞。虽然在其领域内很有价值，但它们对 C 和 C++ 的关注意味着这些数据不适用于 Python/JavaScript 以及主宰现代云原生开发的其他以 Web 为中心的语言。

虽然这些方法各有用途，且有时应当使用，但它们未必反映现代软件开发的现实。真实世界的应用并不是干净、孤立的函数，而是由依赖、框架和业务逻辑编织而成的复杂网络。

我们的方法则不同。我们在 11 个规模较大、基于 Python、积极维护的开源项目上进行测试，这些项目使用常见的 Web 框架（Django、Flask、FastAPI）编写。我们的方法是对以往方法的补充，我们相信它的独特之处在于：a）旨在代表真实世界中 AI 驱动的漏洞挖掘（而非小型的、孤立的合成示例）；b）不受模型训练数据的污染；c）代表了大多数开发者和公司实际在构建的应用类型——使用现代语言和框架的 Web 应用。

### 我们的发现

- 
Claude Code 和 Codex 如今都已具备实用价值：它们能够发现真实的安全漏洞，但噪音非常大。整体噪音依然很高，不过它们确实在这些流行的开源 Python Web 应用中发现了很多真实的安全漏洞。总体而言，Claude Code 发现了 46 个漏洞（14% TPR（真阳性率），86% FPR（假阳性率）），Codex 报告了 21 个漏洞（18% TPR，82% FPR）。

- 
许多 IDOR 缺陷乍看之下判断正确，且 Claude Code 给出了可信的修复建议：LLM 不仅能发现这些缺陷，还能提出可信的修复方案，例如依据代码中已有的模式注入新的权限检查。IDOR 问题往往难以分类排查（triage），为了确认，我们不得不对其中大部分进行实际测试，这也导致真阳性率大幅下降。

- 
Claude Code 能否算是一个好的安全护栏（guardrails）工具？许多发现虽然在技术上是假阳性，但仍然是合理（或看起来合理）的"护栏"建议。例如，模型常常会建议对一条本已安全的 SQL 查询进行参数化。虽然这不是漏洞，但确实增强了代码的健壮性。我们仍将这些视为假阳性，只不过其严重程度不如其他情况。

然而，这些代码加固建议并不总是可信的。我们发现了好几个实例，尤其是在客户端 JavaScript 代码中，AI 试图修复它自认为存在于 DOM 操作方面的问题，但实际上却破坏了代码（在我们观察到的案例中是对 HTML 进行了双重转义），而那里从一开始就不存在任何安全问题。

- 
XSS 和 SQL 注入——难以将各组件拼接到一起：模型很难追踪数据从服务端框架流向客户端组件（这是 XSS 的常见模式），或穿透复杂的应用层。它经常被静态定义的数据所迷惑，或未能识别出服务端的净化处理（sanitization）。

- 
重复提示（prompt）有助于获得更多结果：LLM 的概率特性意味着，以略微不同的方式提出同一个问题就可能产生新的发现，这凸显了分析结果的不一致性。在同一代码库上多次重复同一提示，会得到不同的答案，但最终还是会绕回到相同的发现上。

- 
OpenAI Codex 有时无法输出有效的 SARIF。在我们预期的 66 份报告中，有 9 份不是有效的 SARIF。我们考虑了这些文件中报告的所有发现，但它们并不是有效的 SARIF 或 JSON。在我们尝试的所有情况下，Claude Code 都没有出现这一问题。

## 同一份代码、同一个 AI，每次找出的缺陷却各不相同：AI 编码智能体的非确定性（Non-Determinism）问题

为了探究非确定性在实践中的表现，我们从中选取了三款应用，用同一提示反复运行多次，针对同一个安全问题：IDOR。一个规律浮现出来：每一次运行测试，AI 的发现结果都各不相同。

在漏洞检测的语境下，这是一个重大问题。首先，作为安全工程师，我们理想中希望获得更强的保证——确保我们的代码已经针对重要漏洞类别进行了扫描——而不仅仅是"希望这次模型搜得足够彻底"。

其次，间歇性地检测到漏洞会导致你的安全工具或漏洞管理系统出现不一致和噪音。例如，如果你在使用 SAST（静态应用安全测试）平台、ASPM（应用安全态势管理），或某些内部自建的系统，这些系统往往会假设：当某个此前检测到的漏洞不再出现时，就说明它已被修复。但在 LLM 驱动的检测中，情况可能并非如此——单次扫描可能会漏掉它，于是当后续扫描再次发现同一问题时，就会生成一条"新"发现，进而产生重复的 JIRA 工单并引发开发者的挫败感。

以下是我们观察到的一些具体示例：

- 
PY-APP-007：在第一次运行中，AI 识别出一个"缺少搜索授权"的漏洞，而另外两次运行都没有发现它。第二次运行标记出了该次运行所独有的问题。第三次运行则又发现了一组它自己独有的漏洞。

- 
PY-APP-006：情况类似：第一次运行在用户 API 中发现了一个漏洞，而后续的运行则聚焦于代码库的其他部分，比如活动摘要（event abstracts）和笔记（notes）模块。

- 
PY-APP-002：这里的变异性或许最为明显。识别出的漏洞数量从第一次运行的 3 个跃升至第二次的 6 个，再到 11 个。每次运行呈现的发现都不同，彼此之间只有部分重叠。

那么，背后的原因是什么？我们认为关键因素在于所谓的上下文腐坏（context rot）与压缩（compaction）。当 AI 智能体被指派去分析整个代码库时，它需要处理海量信息：上下文腐坏导致它无法从自己的上下文中准确检索。为了应对这一问题，LLM 使用了一种有损压缩（有时称为 compaction）的方式，这意味着在摘要化过程中，一些更精细的推理细节（如函数名、路径等）可能会丢失。

可以把它想象成尝试为一部又长又复杂的小说写摘要。你会抓住主要情节要点，但必然会遗漏某些细微之处和微妙差别。同理，AI 可能会忘记某个特定的架构模式或某条微妙的数据流，导致它在某次运行中漏掉一个本可在另一次运行中发现的漏洞。我们在 PY-APP-006 中看到了一个清晰的例子：AI 提出的某个修复方案不完整，因为它未能复用一个现有的用户授权基类——而这一关键上下文片段似乎就在那次特定运行中丢失了。

这种非确定性对我们如何打造 AI 原生（AI native）SAST 有着重大影响。一方面，AI 每次都能以不同的方式"思考"，这意味着它可以探索更广泛的潜在攻击向量，就像一支拥有多元视角的人类渗透测试团队一样。另一方面，它也引入了一定程度的不确定性，可能导致困惑或误操作。

- 
覆盖不完整：单次运行可能会带来虚假的安全感，因为它可能漏掉一些在后续运行中才会被发现的严重漏洞。

- 
缺乏可复现性：无法复现结果，使得我们难以验证 AI 的发现，也难以以一致、可重复的方式信任其输出。

- 
成本与时间上升：为了获得更完整的图景而进行多次审计，会显著增加所需的时间和计算资源。注意：对于传统软件，一旦你写好了它，再次运行基本上"免费"（除硬件成本、电费等外）。但对于重度依赖 LLM 的工具来说并非如此——在这种情况下，读取一个代码库并对其推理，每次扫描可能产生数十到数百美元的 Token 成本。对于当今的模型，这一成本或许会随时间推移而下降，但更新的模型可能会更昂贵。

## Claude Code 新增的 `/security-review` 命令效果如何？

Anthropic 为 Claude Code 发布了一个新命令，名为 `/security-review`。它被设计为在拉取请求（PR）上运行，以检查发生变更的文件并提出问题，从而识别具体的安全问题。你可以在这里找到该提示。

当在整个代码库上运行该命令时，我们发现它识别出的安全问题相当有限。很多时候，它无法找到那些当我们提示 Claude Code 一次只搜索某一类特定安全问题时所发现的问题。

我们在 PY-APP-003、PY-APP-002 和 PY-APP-008 上运行了该命令，在所有这些应用中它只发现了一个 XSS，这与我们在整体实验中得到的结果大相径庭。

## 回答我们的问题

让我们基于所学，重新审视我们最初的研究问题。

- 
FP（假阳性）/FN（假阴性）的比率如何？对于真实代码上的原始 AI 而言，假阳性率非常高——最好情况下，Codex 的路径遍历（Path Traversal）为 53%，Claude Code 的 IDOR 为 78%；最差情况下，Claude Code 的 SQL 注入为 95%，Codex 的 SQL 注入或 IDOR 则高达 100%。性能也因应用而异、差异巨大——从 PY-APP-002（Claude Code）中 100%（10/10）的真实 IDOR，到 PY-APP-007 的 0%（0/7）。跨所有应用和所有报告的问题来看，Claude Code 发现了 46 个漏洞（14% TPR，86% FPR），Codex 报告了 21 个漏洞（18% TPR，82% FPR）。

由于我们使用的是真实应用，因此无法在本实验中准确衡量假阴性。我们将在后续的一篇博文中介绍衡量假阴性率的技术方法！

- 
它为什么会失败？我们观察到的主要弱点在于，对于注入类问题，模型缺乏对代码执行的深层语义理解。模型难以处理过程间污点流（inter-procedural taint flow）和隐式流（implicit flows），而这些正是传统 SAST 引擎通常为之构建的能力。此外，部分局限性也源自上下文压缩与上下文腐坏。我们将继续更深入地探究这些局限性，并探索缓解这些问题的解决方案。

- 
脚手架（scaffolding）和智能体式工作流（agentic workflows）有多重要？它们不仅重要，而且正变得不可或缺。AI 在安全评审中的未来，不是单一、庞大的一体化模型，而是一个由 AI 智能体（包括我们案例中的编码智能体）组成的系统——这些智能体能够使用工具、对证据进行推理，并协同工作以发现和验证漏洞。

虽然我们（目前）还没有关于「使用一个可访问 Claude Code 的智能体」与「配合推理模型进行更典型的上下文工程（即构建脚手架以提供所有相关代码）」之间差异的数据，但我们观察到，系统在处理复杂流程、并在报告安全问题的过程中做出明智决策的能力方面存在巨大差异。话虽如此，一个反例是：Sean Heelan 通过充分的上下文工程，得以让推理模型报告一个漏洞（有 8% 的概率）。我们强烈建议你阅读他的博文。

- 
这整个过程中的成本如何？遗憾的是，我们未能统一追踪 Claude Code 与 Codex 之间的成本。针对所有这些漏洞和所有这些应用（不含为测试非确定性和 `/security-review` 命令而进行的运行），Claude Code 的总成本为 114 美元。

## 数据集：未来发布

我们今天暂不发布数据集，也不公布所分析的开源应用的名称，因为我们正处于负责任披露（responsible disclosure）的流程中——正在联系应用开发者，以确保所有安全问题都得到修复和验证。一旦完成，我们便会安心地发布这些数据。

## 结论

LLM 并不是一颗能在明天取代人类安全工程师的灵丹妙药——事实上，它们在端到端地发现高危注入类漏洞方面表现相当薄弱。然而，它们又是一个极其强大的工具。我们的研究表明，通过理解它们的长处（上下文推理）与短处（对代码深层语义的理解），并围绕它们构建精密的智能体式系统、辅以先进的静态分析引擎，我们能够创造出远比以往任何工具都更强大的新一代安全工具。
