# 规格已死，规格万岁！

### 原型是新的规格，而规格是新的……源代码？

在我的职业生涯里，规格文档变得越来越短。我初入 Microsoft 时，一个 PM（产品经理）的价值是用他们规格文档的重量来衡量的。多年后，在 Tripadvisor，我们甚至将那位带着一份潦草地写在餐巾纸上的规格来参加产品评审的 PM 奉为传奇。

产品团队常常把规格当作文书工作——在"真正的工作"（即发布产品）之前的一种必要之恶。工程师因优雅的代码而受到赞誉，设计师因出色的 UX（用户体验）而受到赞誉。PM 因交付影响力而获得嘉许。但规格呢？它们通常被草草赶出、弃之一旁、随即遗忘。

这一直是个错误。在我的产品能力工具箱中，特性规格（Feature Specification）位居首位——在十二项能力中位列第一——这是有原因的。它与产品交付（Product Delivery）和产品质量（Product Quality）一起，支撑着产品执行（Product Execution）。

无懈可击的执行是优秀产品管理的基础，而一份出色的规格则是起跑线。

如今，我们构建产品的方式正在转变。工程师变得越来越快——快得多。AI 能在几分钟内把粗略的想法变成可运行的代码。瓶颈不再是"构建"，而是"知道该构建什么"，以及让团队围绕这些需求达成一致。

突然间，这份卑微的规格不再是转瞬即逝的文书工作。它是产品管理的基础——它正在成为源代码本身。

## 为什么 PM 突然成了瓶颈

在他最近的演讲《用 AI 更快地构建》（Building Faster with AI）中，Andrew Ng 提到了一个前所未有的趋势：

> 
"这是我有生以来第一次看到有人向我提议，让 PM 的数量是工程师的两倍。我仍不确定这个提议是不是个好主意，但我认为它预示着世界的发展方向。" ——Andrew Ng

这印证了我们在此前一篇文章中的预测：随着工程师借助 AI 以数倍的速度交付，公司需要更多的 PM 来支持这些高效的工程师，而不是更少。

随着产品交付加速，这给产品管理的其他所有环节都带来了巨大的压力——理解客户需求、打造正确的特性、验证影响力。

而所有这些压力，最终都汇聚到一件产出物上——规格。

## 规格——新的源代码

在传统软件开发中，程序员编写人类可读的"源代码"，它会被编译成高度优化、机器可读的"目标代码"。"目标代码"（也称为二进制文件）是一种副产品，可以借助源代码重新生成。源代码名副其实，就是"真相之源"。

来自 OpenAI 的 Sean Grove 提出了一个颇具挑衅意味的观点。在他最近的演讲《新代码》（The New Code）中，他主张一份精心编写的提示词（即规格）就是新的源代码。

从这个角度看，我们做 AI 开发的方式是颠倒的。我们精心编写提示词，向模型传达我们的意图。AI 生成代码。然后我们保留代码，丢弃提示词。

"这感觉就像你先把源代码撕碎，然后再小心翼翼地对二进制文件做版本控制，"Grove 如此说道。

想一想这一点。在传统编程中，源代码是神圣的。源代码包含注释、结构和文档——理解并修改系统所需的一切。二进制文件只是下游的产物。

但有了 AI，我们翻转了这种关系。我们把生成的代码当作值得保留的产物，却把规格——即提示词——当作一次性的东西。

Grove 认为这恰恰搞反了。代码，即便是优雅的代码，按他的说法，也只是规格的一种"有损投影"。就像反编译二进制文件无法还原出原始的注释和变量名一样，阅读代码也无法告诉你它背后完整的意图。

而规格则包含一切。一份足够健壮的规格可以生成"优秀的 TypeScript、优秀的 Rust、服务器、客户端、文档、教程、博客文章，甚至是播客"。

"一份足够健壮的规格可以生成优秀的 TypeScript、优秀的 Rust、服务器、客户端、文档、教程、博客文章，甚至是播客。" ——Sean Grove，OpenAI

更重要的是，规格做了代码做不到的事：它让人类和机器围绕共同目标对齐。Grove 简洁地概括道："一份书面规格能有效地对齐人类，它是你用来沟通、讨论、辩论、参照和同步的那件产出物。"

他预测："在不远的将来，最会沟通的人就是最有价值的程序员。而且毫不夸张地说，只要你能有效地沟通，你就能编程。"

新的稀缺技能不再是编程，而是撰写能完整捕捉意图与价值观的规格。

对产品经理来说，这听上去应该很熟悉。这正是我们一直在做的事——只不过现在机器也在听了。

## 等等，原型不是已经干掉了规格吗？

直到最近，产品生命周期还不得不以规格（或 PRD、概念文档、餐巾纸）为起点，从而启动最初的线框图、设计、原型制作和 MVP 开发。

传统做法给人的感觉是一种必要之恶。工程师搭建基础 MVP，只为把某个东西——任何东西——交到客户手中。"如果你的产品第一个版本没有让你感到难为情，那你就发布得太晚了"成了金科玉律。

我们构建产品的整套方法最近经历了一次重大转变，在这个新世界里，规格往往是输出，而不是输入。

如今，你无需发布哪怕一行代码，就能把原型交到客户手中。像 v0、Lovable 和 Replit 这样的工具，能让你在几小时而非几周内构建出可运行的原型。无需任何工程背景。

这不只是更快——而是根本性的不同。凭借一个"氛围编程"式的原型，你可以在写出特性规格的一行字之前，就收集到真实的客户反馈。你可以检验假设、迭代流程、打磨交互。

- 
旧的工作流是这样的：模糊的想法 → 线框图 → 设计 → 工程师搭建的 MVP → 客户反馈 → 痛苦的规格修订 → 线框图 → 设计 → 重建 → 祈祷。

- 
新的工作流：模糊的想法 → 快速原型 → 客户反馈 → 清晰明确的规格 → AI 辅助的实现。

原型并没有干掉规格。它们在让规格变得更好。

## 实践中的规格驱动开发

让我们看一个亲历的实例，了解这一切是如何展开的。Danny Martinez 是 decimals 的创始人，这是一个（处于隐身模式的）平台，帮助创作者经济领域的专家把他们人脉网络中的人才安置到工作岗位上。

- 
你是一位 AI 优先的 PM，正在寻找新的机会吗？留下你的信息，当我们遇到有意思的机会时，我们会通知你。

- 
你是一家想招聘 AI 优先 PM 的公司吗？申请加入我们的人才网络，我们会分享一份精心筛选过的候选人名单。

Danny 将带我们走一遍他们的规格驱动开发流程——这个流程带来了两方面的影响：

- 
对于较大的特性，大幅改善了与工程团队的沟通，以及

- 
让 Danny 这位此前毫无编程经验的人，能够一路从详细的规格走到上线的特性（针对较小的功能）。

这是我最近经手的一个例子。先说下背景，我们在构建一款产品，帮助专家型网红（influencer）把他们网络中的人才安置到工作岗位。在发布了一个新的落地页之后，我们需要给我们的专家们提供一种快速获取自己页面链接的方式。

> 
我们需要在页头（header）放一个按钮，指向公司申请页。我目前正专注于邮件。如果你能接手的话，这个可以氛围编程搞定。

这条消息来自我的联合创始人，指的是一个需要上线的简单按钮。足够简单，而且恰恰是那种现在非技术人员可以自己搞定的活儿。

下面是它如何在几分钟内上线的环境配置和步骤：

- 
项目管理工具：Linear

- 
IDE：VS Code

- 
扩展：GitHub Copilot Pro

- 
模型：Claude Sonnet 4

- 
MCP 服务器：Linear MCP 服务器，让 Linear 的工单（ticket）可以通过 Copilot 访问

让我们看一下这个流程中的步骤（可参照上方的 Loom 视频一起看）：

- 
从联合创始人的 Slack 消息生成一个 Linear 工单（00:14）

-

- 
打开 Copilot，提示 Claude 打开这个 Linear 工单（01:18）

-

-

-

-

- 
等待工程师评审/批准该 PR

拉远视角，这套配置的真正威力就清晰可见了。是的，这是个微不足道的例子，但关键在于：一个非技术人员现在可以在 Linear 工单、代码库和工程师之间来回穿梭，全部只需借助 GitHub Copilot 对 Claude 发出几条提示词。

再说一次，这一切的关键部分并不是代码本身，而是规格。

现在，很重要的一点是，需要说明上述做法要运转良好所依赖的条件：

- 
做到具体（specific）：使用模糊的规格只会导致一团糟的代码库。让 Claude 先拿一份工单的初稿、评审代码库、帮助把它变得更具体，是这个流程中必不可少的一环。在我们的例子里，我们还备有一套写好规格的指南。

- 
做到有选择性（selective）：把上述做法用于更简单的任务是理想的选择。工单越复杂，就越需要一位懂行的人介入（在这些情况下，"自助"最终往往名不副实）。

- 
把关（gatekeeping）：这套做法之所以行之有效，正是因为有一位真正懂行的工程师在评审改动，确保简单性与功能性之间的平衡得以维持。

但我们要把话说清楚：规则已经变了。规格是所有构建该产品的人（包括 LLM）的真相之源。

有了恰当的配置，完全可以期待一个非技术人员为代码库做出贡献。只要有足够的时间和耐心，你可以开始理解代码库并亲自实现改动，而不是每次都单纯依赖 Claude 来救场。

有一天，你甚至可能期待一个 AI 智能体在你喝咖啡的时候，就把你的工单上线了。

如果你是一位 PM，正担心 AI 会对你这份工作做什么，关键是要认识到：这份工作本身正在改变。但这对其他所有人来说也是如此。好消息是，一名出色 PM 所需的核心技能，在这个新世界里反而更有价值了。

正如我们在此前一篇文章中预测的那样，以这种方式运作的公司将需要更多而非更少的 PM。而且事实证明，这个预测应验得相当不错：

## 规格万岁！

科幻作家 William Gibson 曾说过这样一句话——正是他创造了"赛博空间"（cyberspace）这个词：

> 
未来已经到来，只是分布得还很不均匀。

每当我想起 AI 能做和不能做什么时，就会想起这句话。如今，AI 的进展极不均衡。有些事——生成代码、文本、图像——取得了飞跃式的进步，它们以 AI 的速度运转。而另一些事——与客户交谈、发现他们的需求、说服他们购买——仍然以人类的速度推进。

这种不均衡的分布正在重塑产品团队。聚光灯正从实现类工作转向理解类工作。那些一直以来把最优秀 PM 与常人区分开来的核心技能——理解用户需求、清晰地定义问题、设计优雅的解决方案——已经变得指数级地更有价值。

最优秀的 PM 会把这些洞察转化为规格——这些规格能让团队对齐、指导实现，并在这个日益自动化的开发世界里，作为经久留存的那件产出物。

赞同规格是通往基础设施的接口（interface）。

但规格从来就不仅仅关乎代码——它们是想法、价值观和优先级的一种代理（proxy）。

所以没错，更多人能更快地从想法走到原型。但正如你所说，两端——反馈、权衡、决策——仍以人类的速度推进。

在我看来，这不是技术问题，而更多是系统与文化问题。
