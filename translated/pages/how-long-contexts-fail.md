# 长上下文为何会失效

[图: /img/overload.jpg]

### 管理好你的上下文，是智能体成功的关键

随着前沿模型的上下文窗口不断增长1，其中许多已支持多达 100 万个 Token，我看到许多兴奋的讨论，畅想长上下文窗口将如何解锁我们梦寐以求的智能体。毕竟，只要窗口足够大，你大可以把可能需要的一切——工具、文档、指令等等——统统丢进提示里，然后让模型去处理剩下的事。

长上下文一度浇灭了 RAG 的热情（既然能全部塞进提示，何必费力去找最优文档！），催生了 MCP 的热潮（连上所有工具，模型就能胜任任何工作！），也为智能体2的呼声添柴加火。

但现实是，更长的上下文并不会带来更好的回答。让上下文过载，可能会让你的智能体和应用以出人意料的方式失效。上下文可能被污染、分散注意力、造成混淆或彼此冲突。这对智能体尤其致命，因为智能体正是依赖上下文来收集信息、综合结论并协调行动的。

让我们逐一梳理上下文可能失控的种种方式，然后再看看有哪些方法可以缓解甚至彻底规避上下文的失效。

## 上下文的失效方式

- 上下文污染（Context Poisoning）：当幻觉进入上下文

- 上下文分散（Context Distraction）：当上下文压过训练所得

- 上下文混淆（Context Confusion）：当多余的上下文影响了回答

- 上下文冲突（Context Clash）：当上下文各部分彼此矛盾

### 上下文污染

上下文污染指的是，一个幻觉或其他错误混入了上下文，并在其中被反复引用。

Deep Mind 团队在 Gemini 2.5 技术报告中指出了上下文污染问题，我们上周也对此做过解读。在玩《宝可梦》时，Gemini 智能体会在游戏过程中偶尔产生幻觉，从而污染自己的上下文：

>

这类问题中一个尤为恶劣的形态是"上下文污染"——上下文的许多部分（目标、摘要）都被关于游戏状态的错误信息"污染"了，而这种污染往往需要很长的时间才能消除。结果是，模型会执着于追求那些不可能实现或无关紧要的目标。

如果上下文中"目标"部分被污染，智能体就会发展出荒诞的策略，为追求一个根本无法达成的目标而重复行为。

### 上下文分散

上下文分散指的是，上下文变得过长，导致模型过度聚焦于上下文，而忽略了训练阶段学到的东西。

在智能体式工作流中，随着模型收集的信息越来越多、历史不断累积，上下文会持续增长——这些不断累积的上下文可能变得分散注意而非有益。玩《宝可梦》的 Gemini 智能体清楚地展示了这个问题：

>

尽管 Gemini 2.5 Pro 支持 100 万+ Token 的上下文，但如何为智能体有效利用这一能力，仍是一片全新的研究前沿。在这个智能体式设置中，人们观察到，当上下文显著增长超过 100k Token 后，智能体倾向于更偏爱重复其庞杂历史中的既有动作，而不是综合出全新的计划。这一现象虽属轶事，却凸显了"用于检索的长上下文"与"用于多步生成式推理的长上下文"之间的重要区别。

智能体不再运用训练所得来制定新策略，反而执着于重复其庞杂上下文历史中的过往动作。

对于较小的模型，分散注意力的上限要低得多。一项 Databricks 研究发现，Llama 3.1 405b 的模型正确率在 32k 左右开始下降，而更小的模型下降得更早。

如果模型在上下文窗口尚未填满时就开始失常，那么超大上下文窗口的意义何在？简而言之：摘要3和事实检索。如果你做的不是这两件事，那就要警惕你所选模型的分散注意力上限了。

### 上下文混淆

上下文混淆指的是，上下文中的多余内容被模型拿来生成了低质量的回答。

有那么一阵子，似乎人人都要发布一个 MCP。一个强大的模型，连接着你所有的服务和资料，替你处理所有琐碎任务——这个梦想仿佛触手可及。只要把所有工具描述丢进提示里，然后点开始就行。Claude 的系统提示为我们指明了方向，因为其中大多是工具定义或使用工具的指令。

但即便整合与竞争不会拖慢 MCP 的脚步，上下文混淆也会。事实证明，工具太多是会出问题的。

Berkeley Function-Calling Leaderboard 是一个工具使用基准，用于评估模型有效运用工具回应提示的能力。该榜单如今已是第 3 版，结果显示，当提供给模型的工具超过一个时，每个模型的表现都会变差4。此外，Berkeley 团队"设计了所有给定函数都不相关的场景……我们期望模型的输出是不进行任何函数调用"。然而，所有模型偶尔都会调用无关的工具。

浏览这个函数调用榜单，你会发现随着模型变小，问题愈发严重：

[图: /img/gemma_irrelevance.png]

关于上下文混淆，最近一篇论文给出了一个鲜明的例子。这篇论文评估了小模型在 GeoEngine 基准上的表现——该基准包含 46 种不同的工具。当团队把一条查询连同全部 46 个工具交给一个量化（压缩）后的 Llama 3.1 8b 时，它失败了，尽管上下文远在 16k 上下文窗口之内。而当他们只给模型 19 个工具时，它却成功了。

问题在于：如果你把某样东西放进上下文，模型就不得不去关注它。它可能是无关信息或无谓的工具定义，但模型都会将其纳入考量。大模型，尤其是推理模型，在忽略或丢弃多余上下文方面正变得越来越好，但我们仍不断看到无用信息绊倒智能体。更长的上下文让我们能塞进更多信息，但这一能力也带来了代价。

### 上下文冲突

上下文冲突指的是，你在上下文中不断累积的新信息与工具，与上下文中的其他信息发生冲突。

这是比上下文混淆更棘手的一种情况：这里的坏上下文并非无关紧要，而是与提示中的其他信息直接冲突。

微软与 Salesforce 的团队在最近一篇论文中精彩地记录了这一现象。该团队从多个基准中取出提示，并把其中的信息"分片"到多条提示之中。可以这样理解：有时，你可能会坐下来，在按下回车前把每个必要细节都逐段输入 ChatGPT 或 Claude；而另一些时候，你可能会先给一个简单的提示，等聊天机器人的回答不满意时再补充更多细节。微软/Salesforce 团队把基准提示改造成了类似这种多步交互的形式：

[图: /img/sharded_prompt.png]

左侧提示中的所有信息，都被包含在右侧的若干条消息里，这些消息将在多轮对话中逐步展开。

分片后的提示带来了显著更差的结果，平均下降了 39%。而且该团队测试了多款模型——OpenAI 备受推崇的 o3 得分从 98.1 跌到了 64.1。

到底发生了什么？为什么信息分阶段收集而非一次性给出时，模型表现反而更差？

答案就是上下文混淆：被拼装起来的上下文（包含整段对话的完整记录）中，留存着模型在掌握全部信息之前为应对挑战所做的早期尝试。这些错误答案一直留在上下文里，并在模型生成最终答案时对其产生影响。该团队写道：

>

我们发现，LLM 往往在早期回合就做出假设，过早地试图生成最终方案，并对其过度依赖。更简单地说，我们发现，当 LLM 在对话中拐错了弯，它们就会迷失方向，再也回不来了。

这对智能体构建者来说不是个好兆头。智能体从文档、工具调用以及被委派处理子问题的其他模型中拼装上下文。所有这些来自不同来源的上下文，都有可能与自身相矛盾。而且，当你连接那些并非由你创建的 MCP 工具时，它们的描述和指令与提示其余部分冲突的可能性就更大。

百万级 Token 上下文窗口的到来，一度令人感到颠覆性变革。把智能体可能需要的一切统统丢进提示的能力，激发了人们对超级智能助手的想象——能访问任何文档、连接每个工具、保持完美记忆的助手。

但正如我们所见，更大的上下文催生了新的失效模式。上下文污染会埋下随时间不断放大的错误；上下文分散会让智能体过度依赖上下文、重复过往动作而非向前推进；上下文混淆会导致误用无关的工具或文档；上下文冲突则制造出内部矛盾，让推理脱轨。

这些失效对智能体的打击最为沉重，因为智能体恰好运行在上下文最容易膨胀的场景之中：从多个来源收集信息、进行顺序的工具调用、参与多轮推理、并累积庞大的历史记录。

好在，还是有解决办法的！在接下来的一篇文章里，我们会介绍缓解或规避这些问题的技术，从动态加载工具的方法，到搭建上下文隔离区（context quarantine）等等。
