# Coding Agents 101：真正把事情做成的艺术

现在是 2025 年。编码智能体并非魔法，但它们是眼下最接近魔法的东西。我们注意到，一些工程师——尤其是高级（senior）到资深（staff）级别的工程师——比其他人都更快地取得成功。在这里，我们分享一些来自我们客户和我们自身经验的顶级经验教训。

关于本指南：

## 与产品无关

我们讨论的技巧能帮助你在使用任何编码智能体时都取得成功。

## 讲求实战

我们提供我们最喜欢的一些可操作建议。

## 面向技术

虽然编码智能体对许多人都有价值，但本指南是为工程师而写的。

开发者工具一直在快速演进。十年前，是自动补全和智能感知（intellisense），能够提示方法名并执行程序化的重构。四年前，是副驾驶（copilot）和 Tab 补全，能够为你写出接下来的几行代码。两年前，是生成式聊天机器人，能够辅助你的开发并为你生成整个文件。如今，是自主智能体，能够从初始描述一路做到最终的拉取请求（PR），几乎不需要人工干预。过去两年，我们通过构建 Devin 一直专注于实现这一愿景。现在，对自主智能体的兴趣达到了新的高度，尤其是随着近期类似产品的发布 [1] 除 Devin 之外，近期发布的一些产品还包括 OpenAI 的 Codex 和 Google 的 Jules。一些本地智能体，如 Cursor 和 Claude Code，可以在并行的工作区中运行，以复现类似的效果。。这些智能体可以以多种形式出现，包括 Web 应用、移动应用，以及与 Slack、GitHub、Linear 和 Jira 等热门工具的集成。

虽然一个人与 AI 助手配合所能取得的成就会超过任何单独的 AI，但自主智能体端到端处理任务的能力带来了全新层次的多任务处理能力，把每一位工程师都变成了工程管理者。

适应与这些新 AI 同事高效协作可能需要一些时间。有趣的是，我们观察到，高级到资深级别的工程师往往最快接受并精通这些工具。最终，这些工具将在工程的各个层级普及开来。基于我们的经验和客户反馈，我们想分享关键洞见和经验教训，帮助每个人成功地将这些工具融入自己的工作流。

（入门指南）

## 提示基础

这些基本准则将帮助你在 2025 年高效地与编码智能体交互。如果你什么也记不住，至少也要记住这些。

### 说明你想让事情怎么做，而不只是做什么

把智能体想象成一个决策可能不可靠的初级编码搭档。简单的任务可以直接描述，但对于更复杂的任务，要从一开始就清楚地概述你偏好的做法。提前向智能体提供整体架构和逻辑，不仅能提高其成功的概率，还能减少你审查代码的时间，因为你已经熟悉了预期的做法。

#### 示例：

与其说“添加单元测试”，不如明确指出要测试的功能，指出重要的边界情况，并说明（如果有的话）需要 mock 什么。

### 告诉智能体从哪里开始

想想如果是你自己处理这个任务，你会从哪里开始。即使你不知道具体的文件或函数名，也要提到涉及的仓库、相关文档和关键组件。清楚地指出这些要素可以最大限度地减少浪费的精力和困惑。

#### 示例：

“请为我们的代码添加对 Google 模型的支持。你应该查看[这里](link)的最新文档，并在 model groups 目录下创建一个新的实现文件”

### 实践防御式提示

想象把同一条提示交给一个新来的实习生。哪里可能会产生困惑或错误？预判这些点，并主动澄清你的指示，以避免歧义。

#### 示例：

“请修复我们搜索模块的 C++ 绑定，以通过新的单元测试。注意，每次修改代码后，你可能都需要在测试前重新编译这些绑定。”

### 让它能访问 CI、测试、类型和 Linter

智能体的很多魔力来自它们修复自身错误并针对错误消息进行迭代的能力。通过类型检查器、Linter 和单元测试等工具提供强大的反馈回路，可以极大地提升它们的表现。考虑使用带类型的 Python 而非普通 Python，或用 TypeScript 而非 JavaScript。教会你的智能体如何运行常见的检查和测试，确保它拥有所有必需的包和访问权限。如果智能体可以与浏览器交互，请提供关于运行前端开发环境的清晰说明。

#### 示例：

我们团队从大多无类型的 Python SDK 迁移到了完全带类型的 SDK（这也是一个很适合交给编码智能体的任务）。

### 发挥你的专业所长

当你熟悉自己的代码库时，上述一切都变得更容易。即便是简单的任务，也会因你验证逻辑和结果的能力而受益。人类的监督依然不可或缺——归根结底，你要为代码的最终正确性负责。即使这些工具变得越来越精密，所有权和验证仍将是人类工程师的关键职责。

（入门指南）

## 在工作流中使用智能体

[图: Quick wins diagram]

一旦你掌握了与智能体对话的基础，就该把这些 AI 助手带入你的日常工作流了。以下是一些把智能体融入日常的实际做法：

### 立即接手新任务

想象一位同事给你发消息：“嘿，我们能快速把 X 做出来吗？”或者“我们需要微调一下 Y。”与其让它打断你的心流，不如直接给一个自主智能体发送一条简短提示，让它去调查或做出改动。这样你就能腾出手来专注于主要任务。想到一个有趣的副业点子？需要快速做原型、抓取数据或复现研究？把这些交给智能体，稍后再回头查看。

#### 示例：

许多团队在 Slack 上讨论 bug 修复或小的功能更新时，会直接 @Devin。

### 随时随地写代码

想象你在通勤或出差途中，突然冒出一个紧急 bug，或者你意识到自己可能在代码里留了一个错误。别担心！自主智能体通常支持移动端访问，让你能即时处理这些问题。无论是通过 Slack 的移动应用还是专用的移动应用，许多智能体都能让你随时随地解决问题，即使你的 wifi 信号不佳。

#### 示例：

拥有这种灵活性，让我们自己的团队在乘车和飞行途中高效了许多。

### 把琐事交给它

还在为旧提交做二分定位，或为某个新功能更新文档而卡住？把这些重复性任务交给你的智能体。你会省下宝贵的时间，并专注于更有创造性和影响力的工作。

#### 示例：

在我们团队，工程师交付一个改动后，再让智能体去更新所有相关文档和面向用户的文案，是很常见的事。

### 摆脱分析瘫痪

还在纠结某个重构是否真的能简化你的代码？在两个架构方案之间难以抉择？让你的智能体把两个方案都实现出来。有了具体的例子可比较，决策就变得直截了当，而且丢弃某个方案也不会伤到任何人的感情。

#### 示例：

在文本框组件上于 Lexical 和 Slate 之间做选择时，我们让智能体分别实现了二者。Slate 凭借更好的最终效果胜出。

### 搭建预览部署

把你的 CI/CD 流水线设置为每产生一个新的 PR 就自动创建预览部署，让你得到一个即时的线上 URL。这在审查由 AI 智能体完成的前端任务时尤其方便。

#### 示例：

Vercel 是一个让预览部署变得超级简单的部署平台。

## 委派更大的工单

[图: Larger tickets workflow]

[图: Larger tickets workflow]

当你的拉取请求规模和复杂度增长到不止几个文件时，一次性处理就变得很有挑战。然而，掌握如何委派中到大型任务（通常是 1-6 小时的工作量）才是自主智能体回报率最高的地方。你不只是省下几分钟，而是能夺回数小时的生产力。较小的任务可能轻松就能完成，但把智能体的能力拉伸到处理更大任务，才能带来最大的回报。

### 自动化你的初稿

对于规模可观的任务，用自主智能体来生成 PR 的初始草稿，可以启动进度并大幅削减你的工作量。这里的成功取决于从一开始就清楚地传达你期望的做法。把自己想象成指导初级开发者的架构师。清晰、详细的说明有助于避免把不必要的时间花在纠正智能体代码中根本性的误解上。

### 共同编写 PRD

对于复杂或定义模糊的任务，与你的自主智能体协作制定详细计划会非常高效。如果你一开始并不知道每一个细节或需求，这完全没问题。可以先让智能体去探索发现性问题，比如“我们的身份认证系统是如何运作的？”或者“哪些服务可能会受到影响？”你也可以让智能体提前识别出具体的相关代码目标，供你尽早确认。

某些智能体，如 Devin 和 Claude Code，提供专门的规划模式，专注于阅读和探索现有代码，而非立即修改它。如果你希望在委派任务之前做更充分的准备，诸如 deepwiki.com 和 Devin Search 这类专门的代码库搜索工具可以快速为你提供代码库的洞见，帮助理顺流程。

### 设置检查点

对于多部分任务，尤其是涉及多个代码库的任务，要沿途设置清晰的检查点：

计划 → 实现一个分块 → 测试 → 修复 → 检查点评审 → 下一个分块

明确要求在每一个重要阶段之后暂停，尤其是对于跨多个层（例如数据库、后端、前端）构建的复杂功能。利用这些检查点来确保实现符合你的预期，澄清疑问（例如“解释一下认证流程，并确认其安全性”），并尽早纠偏以避免问题级联。

#### 示例：

“我希望你实现这个将横跨我们数据库、后端和多个前端界面的功能。请先规划所需的数据库模式（schema）变更，完成后告诉我，以便我执行迁移。” → “现在请实现后端变更，并添加测试以确保 XYZ 正常工作。完成后告诉我” → “现在请在我们的 Web 和移动界面中都实现调用这个新后端端点的改动”

### 教它验证自己的工作

在给出反馈时，不要只停留在指出问题（“这个函数不工作”）。要清楚地说明你的测试流程，使智能体能够独立地验证未来的任务。对于你会频繁重复的测试模式，将其整合进智能体的永久知识库（参见「添加到智能体的知识库」）。

#### 示例：

在 Devin 中，我们积极提示用户将关键的测试流程保存到智能体的持续记忆中，从而简化未来的交互。

### 在 AI 热点区域提高测试覆盖率

目前，智能体还无法完全地对所有场景进行充分的交互式测试。在 AI 大量修改的区域提高测试覆盖率，可以确保对智能体输出有更强的信心。扎实的测试意味着看起来正确的代码可以被放心地合并，而无需担忧。

#### 示例：

我们团队在把某个实现从 Python 翻译到 C 交给 AI 之前，先强化了代码库中关键部分的单元测试。

（高级）

## 自动化工作流

[图: Workflow automation]

智能体对传入事件的响应速度远快于人类，而且它们比人类同行更乐意去做枯燥、重复的工作。

### 为最重复的工作创建捷径

工程团队经常遇到重复的、例行的任务。这些是交给智能体自动化的绝佳候选。常见示例包括：

- 移除功能开关（feature flag）

- 依赖升级

- 在新功能 PR 上修复和添加测试

要高效地建立这套机制，通常由一位经验丰富的工程师创建一个健壮的、可复用的提示模板 [2] 在 Devin 中，这些被称为 playbook，可以针对这些场景反复运行。

#### 示例：

我们的一个客户在开发新功能时，会自动触发三个专门编写单元测试的智能体。

### 智能代码评审与强制执行

虽然用于快速代码评审的专门工具已经存在 [3] 例如 Greptile 和 CodeRabbit，但自主智能体可以是一个有趣的选择，能给出更精准的洞见，尤其是当它们已经为你的仓库功能建立了索引时。

#### 示例：

在 Cognition，我们喜欢维护一份工程师最常犯错误的清单，并把这份清单提交到代码库中。然后，与其编写传统的 lint 规则来捕捉这些错误（这通常是不可能的），我们让一个智能体在每一个新 PR 上运行来检查这些错误。

### 接入事故与告警

你还可以设置自主智能体以响应特定事件而自动触发。例如，Devin 提供了一个易于访问的接口（API），其他智能体则可以通过 CLI 命令集成到自定义工作流中。这些设置与 MCP 配合使用效果尤佳，以便摄入第三方错误日志。

⚠️ 当涉及对生产服务中的问题做分诊（triage）时，AI 的调试能力并不那么出色。与其要求 AI 在问题出现时端到端地修复 bug，更实际的做法往往是让 AI 只标记出最可疑的错误、变更等。

（高级）

## 自定义与性能提升

### 环境设置

没有什么比一个不完整或不匹配的环境更能拖慢智能体了。为了让一切顺畅运行，要让你的智能体的设置与团队完全一致。这包括语言版本、包依赖和自动化检查。例如，智能体的环境中应该安装 pre-commit，环境配置（密钥、语言版本、虚拟环境、浏览器登录）应该通过诸如 .envrc 或自定义的 .bashrc 配置等工具自动加载。

#### 示例：

我们为智能体的浏览器设置了预先认证的登录，省去了手动认证的麻烦，也让测试轻松许多。

### 构建自定义 CLI 工具和 MCP

MCP 已经广泛可用，并且可以快速搭建和试验，将你的智能体连接到外部工具 [4] 在 Devin 中，MCP 仍处于 beta 阶段，因为我们还在摸索支持它们的最佳方式。如需使用，请联系我们！。但许多人忽略了为智能体搭建简单的 CLI 脚本。举个简单的例子，你可以给智能体一个脚本，让它根据工单 ID 拉取某个 Linear 工单的信息。你可能还想给智能体一个工具来可靠地执行工作流的常见环节，比如一个重启本地开发环境的脚本。

#### 示例：

我们有一个客户通过创建这样一个 CLI 工具取得了很大的成功：该工具只展示测试套件中第一个失败的测试。这个 CLI 会提示智能体带着详细的错误信息只专注于那一个测试，而这一 CLI 让智能体在长任务上拥有更高的成功率和更快的完成率。

### 添加到智能体的知识库

如果你的智能体犯了一些常见错误，这正是把你的反馈固化到智能体知识库（knowledge base）里的好时机。在 Devin 中，有一个专门的知识管理系统。许多产品提供 .rules 文件、.md 文件，供智能体永久摄取。不要只给它关于你所用框架（framework）的指导，还要告诉它你项目的整体架构（architecture）。告诉它不同类型任务通常采用哪种测试方式、如何运行重要命令，以及你推荐使用哪些工具。

#### 示例：

我们给智能体提供知识，告诉它在新增服务路由（service route）时应该遵循的具体流程。这些信息涵盖它需要在前端和后端添加样板代码（boilerplate）的每一个位置。结果，这些任务现在可以轻松地委派给我们的 AI 了。

## 自主智能体的局限性

### 调试能力有限

缺陷（bug）报告可能看起来简单得具有迷惑性。但许多缺陷往往不仅需要访问数据库和日志，还需要超越当今大多数 AI 智能体能力的调试水平。如果使用 AI 辅助调试，我们建议让它列出可能的根因（root cause）清单，而不是试图自己去调试并修复一切。然后，人类可以根据自己的经验判断哪一个才是真正的根因。不过一旦原因确定，智能体在实施修复方面仍然相当有帮助。

### 细粒度视觉推理能力较差

一般来说，当今的模型在匹配设计截图或 Figma 原型（mockup）所需的细节层次上，视觉推理能力并不出色。它们对能在代码层面描述的视觉元素最为可靠（例如给它来自 Figma 的代码）。如果你希望它匹配你的视觉风格，就应该使用一个带有可复用组件（component）的良好设计系统（design system）。

### 知识截止点

每当你想要使用一个新的库（library）时，都应该明确地把它指向最新的文档（docs）。否则，由于预训练基础模型存在知识截止点（knowledge cutoff），大多数智能体会假设采用这些库的旧模式。如果你把它指向文档，一个优秀的智能体可以克服这一点，但你必须对此保持警惕（记住，智能体甚至不知道这些库还有新版本）。

## 管理时间与最小化损失

并不是每次使用智能体都会成功。在 2025 年，这些智能体的结果确实存在一些真实的不确定性。这份工作的一部分内容，就是学会以这样一种方式使用智能体：最大化获得成功结果的概率，同时最小化浪费的时间和 Token。

### 愿意更早止损

对刚开始使用智能体的人来说，一个常见错误是执意要让某次交互成功，即便智能体的工作已经偏离正轨。如果你发现自己冒出"它在无视我的指令"或"这东西在原地打转"这样的念头，你就应该可以放心地终止那次对话，或手动接管。发送更多消息，更可能意味着你的任务固有复杂度超出了智能体的能力，而不是某个可以纠正的简单错误。

### 多样化你的实验

如果你是智能体使用新手，我们建议一开始就分散下注。尝试一系列不同的提示词和想法。在那些你观察到智能体天生表现良好的任务类型上加大投入——并在它们表现不佳的任务上及时止损。不必觉得每一次都必须强迫你的智能体取得成功。

### 进展不顺时就重新开始

与人类相比，重新开始对智能体来说更经常是正确的答案。如果你交给智能体一个任务，而它难以回应反馈或纠正方向，那么用一个新智能体并预先给出所有指令重新开始，往往能更快地取得成功。智能体纠正一团糟环境的能力，远不如它从零开始快速产出全新代码的能力。

## 安全与权限管理

### 为你的智能体创建账户

一个一次性邮箱（throwaway email）有助于安全地测试站点。如果智能体需要访问云资源，请为其创建自定义的 IAM 角色（IAM role）。

### 给它一个开发 / 预发布（staging）环境

理想情况下，智能体使用与你团队工程师相同的测试设置。我们建议完全避免提供生产环境服务的访问权限。使用远程智能体时，你可以在智能体的远程机器上运行完全隔离的测试环境。

### 只读 API 密钥

在可能的情况下，给它只读（readonly）访问权限。我们发现，任何与外部服务交互的脚本，仍然由人类手动运行会更有帮助。

## 前方的大变革

我们坚信软件工程师不会消失。即使编程智能体变得越来越聪明、越来越能干，深厚的技术专长和对代码库（codebase）的深入了解依然无可替代。真正拥有对你的项目、系统和代码的所有权，如今比以往任何时候都更加关键。在我们今天的团队中，工程师被期望在保持深入理解和审慎判断的同时，监督多个系统。随着自动化放大你的影响力，同时处理多项并行任务的能力不仅会变得可行，而且会变得不可或缺。我们很兴奋地分享我们在为自己的组织迎接这一转变过程中所积累的洞见，这样你和你的团队也能够在不断演进的软件开发世界中茁壮成长。
