## API 并不适合作为 MCP 工具

2025 年 8 月 5 日

4 分钟阅读

模型上下文协议（MCP）如今已成为一件相当重要的事情。它已经成为让大语言模型（LLM）能够访问他人编写的工具的事实标准，而这当然会把它们变成智能体。但为一个新的 MCP 服务器编写工具很难，因此人们常常提议把现有接口（API）自动转换为 MCP 工具，通常是借助 OpenAPI 元数据（1、2）。

以我的经验来看，这种做法可行，但效果并不好。以下是几个原因：

## 智能体难以应对数量庞大的工具

众所周知，VS Code 对工具数量有 128 个的硬性上限——但许多模型在远未达到这个数字之前，就已经难以进行准确的工具调用了。此外，每个工具及其描述都会占用宝贵的上下文窗口空间。

大多数 Web 接口（API）在设计时并没有考虑到这些约束！当这些接口由代码来调用时，为单个产品领域提供大量接口是没问题的，但如果把每一个接口都映射为一个 MCP 工具，结果可能就不太理想了。

从头开始设计的 MCP 工具通常比单个 Web 接口灵活得多，每个工具都能完成多个独立接口的工作。

## 接口（API）会迅速耗尽上下文窗口

设想一个接口一次返回 100 条记录，而每条记录都非常宽（比如有 50 个字段）。把这些结果原样发给智能体会消耗大量 Token（令牌）；即使一个查询只需几个字段就能满足，最终每个字段还是都会进入上下文窗口。

接口通常按记录数量进行分页，但记录的大小可能差异很大。一条记录可能包含一个占用 100,000 个 Token 的大型文本字段，而另一条记录可能只有 10 个。把这些接口结果直接塞进智能体的上下文窗口是一场赌博——有时行得通，有时会直接爆掉。

数据的格式也可能是个问题。如今大多数 Web 接口都返回 JSON，但 JSON 是一种 Token 效率非常低的格式。举个例子：

```
[
{
"firstName": "Alice",
"lastName": "Johnson",
"age": 28
},
{
"firstName": "Bob",
"lastName": "Smith",
"age": 35
}
]

```

对比一下同样数据的 CSV 格式：

```
firstName,lastName,age
Alice,Johnson,28
Bob,Smith,35

```

CSV 数据要简洁得多——每条记录消耗的 Token 只有原来的一半。通常来说，CSV、TSV 或 YAML（用于嵌套数据）是比 JSON 更好的选择。

这些问题没有一个是无法克服的。你可以设想自动添加工具参数，让智能体投影字段；自动截断或摘要大型结果；自动把 JSON 结果转换为 CSV（或用于嵌套数据的 YAML）。但我见过的大多数服务器一样都没做。

## 接口（API）未能充分利用智能体的独特能力

接口返回结构化数据，供程序化消费。这通常是智能体希望通过工具调用获得的东西……但智能体也能处理其他更自由形式的指令。

例如，一个 `ask_question` 工具可以对某些文档执行检索增强生成（RAG）查询，然后以纯文本形式返回信息，用于指导下一次工具调用——完全跳过结构化数据。

或者，对 `search_cities` 工具的调用可以返回一份结构化的城市列表，外加一条关于接下来该调用什么的建议：

```
city_name,population,country,region
Tokyo,37194000,Japan,Asia
Delhi,32941000,India,Asia
Shanghai,28517000,China,Asia

Suggestion: To get more specific information (weather, attractions, demographics), try calling get_city_details with the city_name parameter.

```

这种分层和工具链式调用在 MCP 服务器中可能非常有效，而如果你只是自动把接口转换为工具，就会完全错失这一点。

## 如果智能体需要调用接口，它大可直接这么做

如今，像 Claude Code 这样的智能体在编写和执行代码方面能力出众，包括调用 Web 接口的脚本。有些人甚至据此认为，MCP 根本不需要了！

我不同意这个结论，但我确实认为我们应该滑向冰球将要到达的位置。智能体的沙箱隔离正在迅速改善，如果智能体直接调用接口既简单又安全，那我们不妨就这么做，省去中间环节。

## 结论

智能体与接口的典型消费者有着根本性的不同。从现有接口自动创建 MCP 工具是可能的，但这样做效果往往不佳。当智能体拿到的是为其独特能力和局限而设计的工具时，表现才最好。
