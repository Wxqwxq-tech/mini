## 执行摘要

模型上下文协议（MCP）是一项开放标准，它在 AI 模型与外部数据和服务之间架起桥梁，使大型语言模型（LLM）能够以一致、安全的方式进行结构化接口（API）调用。本文将介绍 MCP，说明它为何对连接 AI 系统很有价值，将其与 ChatGPT 插件和手工 API 集成等现有方案进行比较，并深入探讨其近期新增的、基于 OAuth 的身份认证支持。我们还将通过少量代码来一窥 MCP 的实际运行效果。

MCP 充当 AI 工具与外部服务之间的通用适配器，从而无需为每个工具或 API 编写定制集成代码。正如 USB-C 简化了各种设备之间的连接一样，MCP 为 AI 模型调用外部函数、检索数据或使用预定义提示词提供了一种统一的方法。就其核心而言，MCP 提供一个可连接众多不同系统的单一接口。

## 什么是模型上下文协议 MCP？

MCP 本质上是 AI 应用与外部工具或数据源之间的通用适配器。它定义了一种通用协议（构建于 JSON-RPC 2.0 之上），让 AI 助手能够以结构化方式从外部服务调用函数、获取数据或使用预定义提示词。无需每个 LLM 应用为每个 API 或数据库编写定制代码，MCP 为所有交互提供了一套标准化的“语言”。

MCP 层使 AI 应用能够安全地访问外部数据源和工具并与之交互。它充当大型语言模型（LLM）与各类数据库、应用或 API 之间的桥梁，在无需大量定制编码的情况下实现无缝集成与功能。

为此，MCP 采用客户端-服务器架构。AI 驱动的应用（例如聊天机器人、IDE 助手或智能体）充当宿主并运行一个 MCP 客户端组件，而每个外部集成则以 MCP 服务器运行。服务器通过 MCP 协议对外暴露能力（如函数、数据资源或提示词模板），客户端则连接服务器以利用这些能力。这种分离意味着 AI 模型并不直接与 API 通信，而是经由 MCP 客户端/服务器的握手过程，由后者来组织交互的结构。

## 为什么 MCP 有价值

在传统方案中，将 AI 模型连接到外部数据或操作既繁琐又零散。开发者通常不得不为希望模型使用的每个 API 或数据库编写一次性集成代码，为每个都要处理不同的认证方式、数据格式和错误处理。MCP 通过标准化这些交互改变了这一局面。主要优点包括：

- 快速集成工具：借助 MCP，你无需从头为每个能力编写定制代码即可接入新的能力。如果已有针对 Google Drive 或 SQL 数据库的 MCP 服务器，任何兼容 MCP 的 AI 应用都能连接到它并立即获得相应能力。这对自动化而言是一大胜利——AI 智能体只需添加相应的服务器，就能按需获取文档、查询数据库或调用 API。这就像拥有一个由现成“插件”组成的库，而所有插件都使用同一种语言。MCP 服务器充当轻量级程序，通过标准化协议对外暴露特定能力，在 Cursor 与各种外部工具或数据源之间起中介作用。

- 自主智能体：MCP 赋予 AI 更自主的行为。智能体不再局限于其内置知识，它们可以在多步骤工作流中主动检索信息或执行操作。例如，一个复杂的智能体可以通过 MCP 从 CRM 系统收集数据，随后通过通信工具发送电子邮件，再在数据库中记录一条数据——所有这些都在一条无缝的链条中完成。通过支持流畅、上下文感知的多步骤交互，MCP 帮助 AI 智能体向真正的自主任务执行更进一步。正如一位观察者所言，MCP 通过让 AI 获得对现实世界工具和数据的标准化访问，将其从孤立的“大脑”转变为多功能的“行动者”。

- 降低摩擦与搭建成本：由于 MCP 充当通用接口，开发者得以避免维护彼此独立集成所带来的碎片化。一旦某个应用支持 MCP，它就能通过单一机制连接任意数量的服务。这大幅减少了每次想让 AI 使用新 API 时所需的手动搭建工作。团队可以专注于更高层次的逻辑，而不必第 10 次重新编写连接代码。正如 Anthropic 所说，MCP 用一套更简单、更可靠的单一数据访问协议取代了碎片化的集成。

- 一致性与互操作性：MCP 在各类工具之间强制采用一致的请求/响应格式。这意味着你的 AI 应用无需为服务 A 处理一种 HTTP 响应、为服务 B 处理另一种 XML 等。模型的输出（函数调用）与工具结果都以统一的 JSON 结构传递。这种一致性让调试和扩展都变得更加容易。它也让你的集成逻辑面向未来——即便你更换底层的模型供应商，MCP 与工具之间的接口仍保持不变。

- 双向上下文：与简单的 API 调用不同，MCP 支持在模型与工具之间维护上下文并进行持续对话。除了工具之外，MCP 服务器还可以提供提示词（针对特定任务的预定义提示词模板）和资源（文档之类的数据上下文）。这意味着 AI 不仅能“调用 API”，还能摄入参考数据或遵循由服务器引导的复杂工作流。该协议的设计初衷就是支持丰富的交互，而非仅仅一次性的查询。这在编码助手（AI 可通过 MCP 与开发环境反复交互）或需要与各种数据源来回交互的复杂决策任务等应用中尤为有用。

简而言之，MCP 为增强 LLM 带来了一种可扩展、即插即用的方式。它让 AI 系统能够安全地接入所需的“实时”数据和操作，而无需每个开发者都重复造轮子。MCP 的早期采用者已为 Google Drive、Slack、GitHub、数据库等工具构建了服务器——展示了 AI 智能体如何借助 MCP 与企业内容库、开发运维工具以及其他现实世界系统协同工作。

### 客户端-服务器结构

MCP 遵循清晰的客户端-服务器架构：

- MCP 客户端：内嵌于 AI 应用（聊天机器人、IDE 助手、自动化智能体）中。

- MCP 服务器：对外暴露外部能力，如函数（工具）、资源（数据）和提示词（模板）。

所有交互都通过标准化的 JSON-RPC 消息进行，从而维持安全、结构化的交互：

示例 JSON-RPC 请求：

例如，要列出可用工具，MCP 客户端会发送如下请求：

```
{
"jsonrpc": "2.0",
"id": 1,
"method": "tools/list",
"params": {}
}
```

服务器会以一个结构化的 JSON 回复，列出这些工具（每个工具都带有名称、描述和输入 schema）。例如，某个服务器可能会公布一个 get_weather 工具，并描述它需要哪些输入。

```
{
"jsonrpc": "2.0",
"id": 1,
"result": [
{ "name": "get_weather", "description": "Retrieves weather data.", "schema": { "location": "string" } }
]
}
```

稍后，当 LLM 决定使用某个工具时，客户端会发起一次调用。MCP 服务器执行该函数，并以结构化的 JSON 响应返回结果。随后，MCP 客户端（位于宿主应用内）可以将该结果反馈到模型的上下文或响应中。实际上，宿主应用在此过程中起中介作用：它将 LLM 的意图（通常通过模型的函数调用输出来表达）转化为 MCP 请求，再把服务器的结构化结果传回 LLM。这种双向交互既安全又可控——模型只能调用服务器所暴露的特定工具，所有进出数据都经过既定协议。

## 构建与部署 MCP 服务器

构建与部署 MCP 服务器是利用模型上下文协议（MCP）进行 AI 集成的关键一步。MCP 服务器在 AI 模型与外部数据源或工具之间充当中介，实现无缝的通信与数据交换。MCP 的突出特性之一是其服务器开发的灵活性。开发者可以使用任何能够向 stdout 打印输出或提供 HTTP 端点的编程语言，从而选择自己偏好的语言和技术栈。

在构建 MCP 服务器时，考虑架构与设计至关重要。MCP 遵循客户端-服务器架构，其中宿主应用可以连接多个服务器。这种架构带来了可扩展性与灵活性，使开发者能够设计出处理各类任务和功能的 MCP 服务器，例如数据处理、工具集成或 AI 模型管理。

MCP 服务器可以在各种环境中部署，包括本地开发环境、云平台或本地（on-premises）基础设施。例如，Cloudflare 为构建和部署远程 MCP 服务器提供了强大的平台，使 MCP 部署的管理与扩展更加轻松。这种灵活性确保 MCP 服务器能够针对不同应用和环境的具体需求进行定制，无论是用于开发的本地环境，还是用于生产的云方案。

通过专注于精心设计的架构并善用 MCP 的灵活性，开发者可以创建强大且可扩展的 MCP 服务器，从而增强 AI 模型的能力，使其能够与外部数据源和工具无缝交互。

## MCP 客户端与工具

MCP 客户端与工具是模型上下文协议生态系统的关键组成部分。MCP 客户端是连接 MCP 服务器以访问外部数据源或工具的应用程序。这些客户端可以使用多种编程语言和框架来构建，例如 Python、JavaScript 或 Java，让开发者能够灵活地为自身具体需求选择最佳工具。

另一方面，MCP 工具则是为 MCP 客户端提供特定能力或功能的软件组件。这些工具可以与 MCP 服务器集成，以支持数据处理、AI 模型管理或工具集成等功能。MCP 工具的示例包括 Claude Desktop（提供与 AI 模型交互的聊天界面）和 Cursor（提供用于扩展 AI 能力的插件系统）。

开发者可以构建自定义的 MCP 客户端和工具，以满足特定的使用场景或需求。这种灵活性促进了 MCP 生态系统的创新与实验，使开发者能够创造出新颖且令人兴奋的应用。无论是用于数据分析的专用工具，还是与多个 MCP 服务器集成的客户端应用，可能性都非常广阔。

通过善用 MCP 客户端和工具，开发者可以构建稳健且多功能的应用程序，充分发挥 AI 模型的潜力，使其能够与各种外部数据源和工具无缝交互。

让我们比较一下在 MCP 之前或与 MCP 同时存在的一些方案：

- 定制集成与 API 密钥管理：最常见的传统做法是为每个服务编写定制代码，并向 LLM 提供凭据（API 密钥或 Token）以使用这些集成。例如，你可以编写一个 Python 函数来查询某个 API，让 LLM 具备调用该函数的能力，并在后端手动管理 API 密钥。这种方法费时费力且难以扩展——每个新数据源都需要新代码，每个环境都必须安全管理 API 密钥。由于每个集成都是独一无二的，它往往导致系统脆弱。相比之下，MCP 将这些交互集中化并标准化：AI 智能体只需处理 MCP 协议，任何 MCP 服务器（针对任何服务）都能以即插即用的方式工作。可以添加新服务器而完全无需改动客户端代码。此外，MCP 还提供了正式的身份认证结构（稍后讨论），使得向 AI 提供 API 密钥不再是临时为之，而是通过安全协议完成。

- ChatGPT 插件（OpenAI 插件）：2023 年，OpenAI 为 ChatGPT 引入了插件系统，允许模型调用由 OpenAPI 规格定义的 API。这是迈向标准化工具使用的重要一步，但它也有局限性。每个插件本质上都是自己的小型集成（带有各自的 API schema 和身份认证），并且需要单独构建/托管。由于这是一种专有方案，只有特定平台（如 ChatGPT 或 Bing Chat）才能使用这些插件。此外，插件大多是单次调用——模型会调用 API 并获取信息，而没有持久连接或持续交互。MCP 的不同之处在于它是开放且通用的（不绑定于某一供应商或接口），并支持丰富的双向交互和持续上下文。可以把 ChatGPT 插件想象成一个封闭工具箱中的专用工具，而 MCP 则是一个任何开发者或 AI 平台都能使用的开放标准工具集。MCP 标准化的身份认证（尤其是 OAuth）还意味着，与 ChatGPT 系统中逐插件的 OAuth 流程相比，它能够以更统一的方式安全访问用户数据。总而言之，ChatGPT 插件展示了为 LLM 标准化 API 访问的价值，但 MCP 更进一步，将其变为开放协议，并在 AI 与服务之间实现了持久的“对话”。

- LLM 工具框架（LangChain、智能体库）：在 MCP 出现之前，许多开发者使用 LangChain 之类的框架来为模型提供工具。在这些方案中，你定义一组工具函数（带描述）以及智能体的提示逻辑，让 LLM 能够决定是否使用它们。这种方法可行，但每个工具在幕后仍需定制实现——LangChain 最终在其库中维护了数百个工具集成。本质上，LangChain 提供的是面向开发者的标准（一个 Python 类接口），用于将工具集成到智能体的代码库中，但并没有为模型在运行时动态发现新工具提供任何支持。MCP 与这些框架是互补关系，它将标准化转移到面向模型的一侧。有了 MCP，智能体可以发现并使用 MCP 服务器提供的任何工具，即便智能体的代码事先并未显式包含该工具。事实上，LangChain 已经增加了相应支持，可以将 MCP 服务器当作又一个工具来源——这意味着用 LangChain 构建的智能体可以轻松调用 MCP 工具，充分利用不断壮大的 MCP 服务器生态系统。区别在于，MCP 通过协议（JSON-RPC 以及元数据等）将接口形式化，使其更容易接入不同环境，而不仅仅是 Python 框架。类似地，OpenAI 的原生函数调用功能可视为处理函数调用的格式化（模型输出一个 JSON 函数调用），而 MCP 则以标准化方式处理该调用的执行。OpenAI 的函数调用与 MCP 常常协同工作：LLM 生成结构化调用，MCP 客户端/服务器执行它并返回结果，二者共同实现无缝的工具使用。

本质上，MCP 并非首次尝试将 LLM 与外部 API 连接起来——但它从过去那些方案（插件、工具库等）中汲取了经验，并统一了解决方案。它提供了一种开放的、与模型无关的协议，简化了集成与身份认证。尤其是在安全与认证方面，MCP 的设计（支持 OAuth）避免了过去那种"每个插件一把钥匙"或把原始 API 密钥直接交给模型的做法。相反，身份认证可以作为协议的一部分，以一种一致、标准化的流程来处理——相比现状是一大进步。

## MCP 实战：技术深入解析

让我们逐步走一遍一次典型的 MCP 交互，以夯实对它的理解，并看一点代码。设想我们有一个 AI 助手，想使用一个提供一组工具的 MCP 服务器（比如一个假想的 "Neon" 数据库服务）。高层流程如下：

1. 连接到 MCP 服务器——宿主应用（AI 助手）初始化一个 MCP 客户端，并与服务器建立连接。根据服务器所处的位置，这可能是通过本地进程（stdio）或远程 HTTP 流（SSE）。在底层，客户端会发送一条 initialize 消息，以握手协商协议版本与能力。

2. 发现可用的工具/资源——客户端随后查询服务器提供的内容。如前所示，它可能发送 {"method": "tools/list"} 并得到一份工具定义列表。助手可以利用这些信息告知 LLM（例如，把工具列表放入系统提示中，或通过模型的功能 schema，取决于具体实现）。例如，使用某个 SDK 时，这可以是一行代码，形如：

```
const tools = await mcpClient.request({ method: 'tools/list' }, ListToolsResultSchema);
```

它会返回一份结构化的工具列表。每个工具条目都包含名称、描述以及输入的 JSON schema，这样 AI 就知道自己能做什么。

3. LLM 选择工具——当用户向 AI 提出一个需要外部操作的请求时，LLM 会判定（通常通过提示工程或函数调用能力）应当使用某个工具。例如，用户问："AAPL 股票的最新价格是多少？" LLM 意识到它应当调用 get_current_stock_price(company="AAPL", format="USD")。宿主应用捕获这一意图（例如，OpenAI 的函数调用 API 会以 JSON 形式返回函数名与参数）。

4. 通过 MCP 调用工具——客户端现在向服务器发送一条 tools/call 请求，带上所选工具的名称与参数。我们此前见过这样一条示例 JSON。在代码中，使用某个 SDK 时，它可能形如：

```
const result = await mcpClient.request({
method: 'tools/call',
params: { name: toolName, arguments: toolArgs }
}, CallToolResultSchema);
```

这将使服务器在其一侧执行该工具的处理程序。服务器可能会调用某个外部 API、执行一次数据库查询，或运行该工具所封装的任意逻辑。结果（可能是一个简单值，也可能是一个复杂的 JSON 对象）会在 MCP 响应的 result 字段中返回。

5. 将结果返回给 LLM——MCP 客户端收到该工具的输出。此时宿主应用可以将其整合回 AI 的响应中。在许多智能体（agent）设置中，常见模式是把结果注入对话，并让模型继续。例如，助手随后可能呈现："AAPL 当前股价为 $173.22（USD）。" 若使用自动循环，结果可以交给模型（或许以类似 "Result of get_current_stock_price: ..." 的系统消息追加到对话中），模型便可带着这一信息继续回答用户的提问。

下面是一个使用 Anthropic 的 Claude（原生支持工具使用）调用工具并在对话中使用结果的简化示意：

```
// 1. Send user prompt to LLM with available tools context
const response = await anthropicClient.complete({
prompt: "User: Can you list my projects?\nAssistant: ",
model: "claude-3.5",
tools: tools // list of tools from MCP server
});
for (const msg of response.messages) {
if (msg.type === 'tool_use') {
// 2. LLM decided to use a tool
const { name, args } = msg;
// 3. Call the tool via MCP
const toolRes = await mcpClient.request({ method: 'tools/call', params: { name, arguments: args } });
// 4. Inject tool result and resume LLM
await anthropicClient.send({ role: 'system', content: `Tool result: ${toolRes.result}` });
} else {
// 5. Handle normal LLM reply (tool result likely integrated)
console.log("Assistant:", msg.content);
}
}

```

实际上，框架会帮你处理其中大量工作，但上述伪代码勾勒出了 MCP 如何融入这个循环。关键点在于，MCP 为工具执行提供了标准化的调用/响应层，AI 智能体代码可以挂接其上。无论你使用 OpenAI、Anthropic 还是其他 LLM，MCP 都保持不变——它是模型意图与外部操作之间的粘合剂。

通过使用 MCP，开发者获得了一条清晰、结构化的流水线来扩展 AI 能力。代码变得更易维护（因为你在各处调用的是通用的 mcpClient.request，而不是针对每个服务写一套特定代码），AI 也变得更强大（因为它可以接入任何已连接 MCP 的服务）。调试也更容易——你可以监控 JSON-RPC 消息，精确查看请求了什么、返回了什么，而不必去解析模型生成的文本来寻找线索。

## 早期局限（缺少内置身份认证）

当 MCP 最初出现时（2024 年末），它提供了工具与数据交换的核心协议，但缺少用于连接远程服务器的标准化身份认证机制。实践中，早期的 MCP 演示与实现通常要求把 MCP 服务器运行在本地或受信任的环境中，在那里身份认证并不是大问题（因为 AI 与服务器运行在同一台机器上）。例如，开发者可以用一个预先取得的 token 在本地 localhost 上运行一个 Google Drive 的 MCP 服务器，然后让他们的 AI 应用指向它。但要在互联网上或与第三方服务一起使用 MCP，在没有正式认证流程的情况下就很棘手。

许多早期的 MCP 服务器假设用户会在启动时手动向服务器提供凭据或 API 密钥。例如，Anthropic 的快速入门建议通过配置或命令行提供你自己的凭据（API 密钥、token）来运行预构建的服务器。这意味着服务器本身可以访问你的密钥，而 MCP 客户端只是信任该服务器。虽然这对个人或单用户场景有效，但对多用户应用或云托管的智能体来说扩展性不佳。没有标准的握手流程让 AI 智能体说："嘿，我被允许代表用户 X 访问这个服务；这是我的凭据。"

本质上，早期的 MCP 客户端除了通过带外方式（如预先共享一个 token，或在不启用认证的情况下运行）之外，无法对 MCP 服务器进行身份认证。这是一个显著的局限——MCP 本就被设计为开放且基于互联网的，但缺少认证标准，安全的远程使用就受到了掣肘。

认证标准的缺失意味着 MCP 客户端无法自行安全地连接任意服务器。你要么把客户端 ID/API 密钥硬编码到客户端中（这在分布式应用中并不理想），要么只能在无认证的情况下运行，并假定只有获授权的用户才能触达服务器（通常通过将其保留在本地来实现）。显然，要让 MCP 充分发挥潜力（例如以安全的方式将 AI 智能体连接到云托管的数据源），需要一种更好的方案。好消息是，社区认识到了这一点，并着手将基于 OAuth 的身份认证融入 MCP。

### OAuth 2.0 认证流程

为解决最初的认证局限并增强安全连接，MCP 采用了 OAuth 2.0——一种广受认可且稳健的认证标准。OAuth 2.0 提供了一种安全、可扩展的框架，使 MCP 客户端能够安全地与远程服务器、云托管资源以及多用户环境交互。将 OAuth 2.0 集成到 MCP 中的关键组件与益处包括：

- 动态客户端注册（DCR）：模型上下文协议支持动态客户端注册，允许客户端自动向 OAuth 服务器注册。这消除了手动客户端配置或硬编码凭据的需要，显著简化了开发者的部署流程。

- 自动端点发现：MCP 利用标准化的元数据 URL（遵循 OAuth 的发现协议），让客户端自动发现 OAuth 端点。这减少了配置开销，使 MCP 部署更加简单灵活。

- 安全的授权与令牌管理：客户端安全地获取与用户权限和访问范围精确匹配的 OAuth 令牌。这确保客户端只访问用户明确允许的资源，从而提升安全性与合规性，尤其是在多用户与云环境中。

- 可扩展且安全的多用户支持：OAuth 2.0 的设计天然支持多个并发用户与服务，解决了 MCP 早期一个显著的局限。应用现在可以无缝地同时处理众多用户的授权流程，这对云的广泛采用至关重要。

## 调试与故障排查

调试与故障排查是使用 MCP 服务器和客户端时的关键环节。MCP 提供了多种工具与技术用于调试和故障排查，确保开发者能够高效地识别并解决问题。这一过程中的关键工具之一是 MCP Inspector，一个用于 MCP 服务器的交互式调试工具。

MCP Inspector 让开发者能够测试和检查 MCP 服务器，识别并解决 MCP 服务器集成中的问题。该工具提供了 MCP 客户端与服务器之间交互的详细视图，使定位问题、理解其根本原因更加容易。此外，MCP 还提供了一份全面的调试指南，概述了常见问题与解决方案，帮助开发者快速排查并解决问题。

在调试 MCP 服务器时，考虑系统的架构与设计至关重要。开发者应识别出导致问题的具体组件或模块，并使用 MCP Inspector 之类的工具来诊断并解决问题。通过专注于系统化的调试方法并善用现有工具，开发者可以确保他们的 MCP 集成稳健可靠。

## MCP 的实际应用

模型上下文协议（MCP）在众多行业与领域都有各种实际应用。MCP 的一个主要用例是在 AI 集成中，MCP 使 AI 模型与外部数据源或工具之间的通信与数据交换能够无缝进行。

MCP 可用于各种应用，例如：

- 构建 AI 驱动的聊天机器人：这些聊天机器人可以访问外部数据源或工具，为用户提供准确且最新的信息。

- 创建 AI 驱动的工作流：MCP 使 AI 模型能够与外部系统或数据源集成，自动完成复杂工作流并提升效率。

- 开发 AI 模型：这些模型可以与外部工具或数据源交互，增强自身能力并产出更准确、更相关的输出。

- 支持 AI 驱动的自动化：在金融、医疗或制造等行业中，MCP 可以自动化任务与流程，提高生产力并减少错误。

MCP 的灵活性与适应性使其成为希望在其应用中利用 AI 与机器学习的开发者和组织的一个有吸引力的解决方案。通过为 AI 模型与数据源及工具的交互提供标准化接口，MCP 促进了 AI 生态系统的创新与实验。这种标准化方法不仅简化了集成过程，还确保 AI 模型能够访问到其发挥最佳表现所需的数据与工具。

总而言之，MCP 为 AI 应用打开了一个充满可能的世界，让开发者能够创建更集成、更自主、更可扩展的解决方案。无论是用 AI 驱动的聊天机器人提升客户服务，还是在工业场景中自动化复杂工作流，MCP 都提供了将这些创新付诸实践所需的工具与框架。

## 结论

模型上下文协议（MCP）是 AI 开发领域一项激动人心的发展，因为它让开发者能够安全、高效地将我们日益智能的语言模型连接到此前难以连接的广阔软件与数据世界。通过引入一个通用协议，MCP 让我们能够构建更集成、更自主、更易于扩展的 AI 系统。我们不再需要为每个新工具编写一次性插件或给模型塞入脆弱的指令，而是拥有一个连贯的框架，让 AI 智能体能够在适当监管与安全保障下即时发现并使用工具。

尽管该协议仍在演进（身份认证是近期才加入的，而标准化服务器发现等更多特性也已在规划中），但很明显，MCP 或类似的机制将在下一代 AI 应用中扮演关键角色。对开发者而言，现在正是熟悉 MCP 概念的好时机。无论你是要用公司专属知识增强聊天机器人，还是构建一个自动化工作流的 AI 智能体，MCP 都能通过处理工具集成中的"管道"工作，为你节省时间、减少麻烦。而且，由于它是一个由日益壮大的社区（以及 Anthropic 等公司）支持开放标准，未来很可能会成为 AI 基础设施的一块基石。

总而言之，模型上下文协议开启了一个这样的世界：AI 助手不再是孤立的"天才"，而是装备精良的工程师与助手——能够与众多系统对接、遵循流程、按需获取或创建信息，而这一切都通过一个统一、安全的接口完成。这是一个强大的愿景，也正随着 MCP 迅速成为现实。
