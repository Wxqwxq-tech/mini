OpenAI 如何使用 Codex

<!-- page 3 -->
引言
在 OpenAI，Codex 被安全（Security）、产品工程（Product Engineering）、前端（Frontend）、API、基础设施（Infrastructure）以及性能工程（Performance Engineering）等众多技术团队日常使用。团队正借助它加速一系列工程任务，从理解复杂系统、重构大型代码库，到发布新功能以及在紧迫的截止日期下处理事故。
基于对 OpenAI 工程师的访谈以及内部使用数据，我们整理出这些使用场景与最佳实践，以展示 Codex 如何帮助我们的团队更快推进工作、提升工作质量，并在规模化下管理复杂性。

使用场景 1
代码理解
在入职、调试或排查事故时，Codex 帮助我们的团队在代码库中不熟悉的部分快速上手。
工程师经常使用 Codex 定位某个功能的核心逻辑、梳理服务或模块之间的关系，以及追踪数据在系统中的流转。它还能揭示架构模式或缺失的文档片段，而这些若靠人工生成则需要大量工作。
在事故响应期间，Codex 通过揭示组件之间的交互、追踪失败状态如何在系统间传播，帮助工程师快速切入新的领域。
来自我们团队的轶事
当我修复一个 bug 时，我会用 Ask 模式查看代码库中其他地方是否可能出现同样的问题。
性能工程师，检索系统（Retrieval Systems）
值班时，我会粘贴堆栈跟踪信息，并询问 Codex 认证（auth）流程在哪里。它会直接跳到正确的文件，让我能快速分流处理。
站点可靠性工程师（SRE），API 平台
Codex 能跨越 Terraform 和 Python 回答我「我应该在哪里做这件事？」这类仓库问题，比 grep 快得多。
DevOps 工程师，基础设施服务
试试用以下示例提示让 Codex 做代码理解：
这个仓库中的身份认证（authentication）逻辑是在哪里实现的？
总结请求如何从这个服务的入口一路流向响应。
哪些模块与[插入模块名称]交互，失败又是如何被处理的？

使用场景 2
重构与迁移
Codex 常被用来进行跨多个文件或包的修改。例如，当工程师在更新某个 API、改变某种模式的实现方式，或迁移到新的依赖时，Codex 能让这些修改被一致地应用。
当同样的更新需要跨数十个文件进行，或更新需要感知那些用正则表达式或查找替换难以捕捉的结构与依赖时，它尤其有用。
工程师还用它来做代码清理，例如拆分过大的模块、用现代模式替换旧模式，或为代码做更好的可测试性准备。

按关注点将这个文件拆分为独立的模块，并为每个模块生成测试。
将所有基于回调（callback）的数据库访问转换为 async/await。

使用场景 3
性能优化
Codex 被用来识别和解决性能瓶颈。
在调优或可靠性改进过程中，工程师会提示 Codex 分析缓慢或内存密集型的代码路径，例如低效的循环、冗余的操作或代价高昂的查询，并给出优化后的替代方案，往往能带来效率与可靠性的显著提升。
Codex 还被用来支持代码健康，识别仍在活跃使用中但有风险或已弃用的模式。我们的团队依赖它来帮助减少长期技术债，并主动预防回归。
来自我们团队的轶事
我用 Codex 扫描重复的、代价高昂的数据库（DB）调用。它很擅长标记热点路径，并起草我可以稍后调优的批量查询。
基础设施工程师，API 可靠性
Codex 很擅长快速发现性能问题——我花 5 分钟写提示，就省下了 30 分钟的工作量。
平台工程师，模型服务（Model Serving）
试试用以下示例提示让 Codex 做性能优化：
优化这个循环的内存效率，并解释为什么你的版本更快。
找出这个请求处理器中重复的代价高昂的操作，并建议缓存的机会。
为这个函数建议一种更快的批量数据库查询方式。

使用场景 4
提升测试覆盖率
Codex 帮助工程师更快地编写测试——尤其是在覆盖率薄弱或完全没有覆盖的地方。
在进行 bug 修复或重构时，工程师经常请 Codex 建议覆盖边界情况或可能失败路径的测试。对于新代码，它可以根据函数签名和周边逻辑生成单元测试或集成测试。
Codex 在识别边界条件方面尤其有帮助，例如空输入、最大长度，或那些在最初的测试中常常被忽略的、罕见但合法的状态。
来自我们团队的轶事
我在夜里让 Codex 处理低覆盖率的模块，醒来就能看到可运行的单元测试 PR。
前端工程师，ChatGPT Desktop
当切换单仓库（mono-repo）分支很痛苦时，我让 Codex 编写测试并触发 CI，而我继续在自己的分支上工作。
后端工程师，支付与账单（Payments & Billing）
试试用以下示例提示让 Codex 提升测试覆盖率：
为这个函数编写单元测试，包括边界情况和失败路径。
为这个排序工具生成一个基于性质（property-based）的测试。
扩展这个测试文件，覆盖 null 输入和非法状态等缺失的场景。

使用场景 5
提升开发速度
Codex 通过同时加速开发周期的起点和终点，帮助团队更快推进。
在启动新功能时，工程师用它搭建样板代码（boilerplate）——生成文件夹、模块和 API 桩（stub），从而快速得到可运行的代码，而无需手工逐项接线。
随着项目临近发布，Codex 通过处理较小但关键的任务来帮助赶上限期，例如分流 bug、填补最后一公里的实现缺口，以及生成发布脚本、遥测（telemetry）钩子或配置文件。
它还被用来把产品反馈转化为起始代码。工程师经常粘贴用户请求或规格（spec），让 Codex 生成一个粗略的草稿，以便之后返回并进一步打磨。
来自我们团队的轶事
我整天都在开会，却仍然合并了 4 个 PR，因为 Codex 一直在后台工作。
产品工程师，ChatGPT Enterprise
Codex 完美地交付了 3-4 个低优先级的修复，这些修复原本会在待办列表（backlog）里积压，这让人非常有成就感。
全栈工程师，内部工具（Internal Tools）
试试用以下示例提示让 Codex 提升开发速度：
为 POST /events 搭建一个新的 API 路由，包含基本的校验和日志记录。
使用这个模板[插入你的遥测代码示例]，为跟踪新用户引导流程的成功/失败生成一个遥测钩子。
基于这个规格创建一个桩实现：[插入规格或产品反馈]。

使用场景 6
保持心流
Codex 帮助我们的工程师在日程被碎片化、充满干扰时依然保持高效。
它被用来记录未完成的工作、把笔记转化为可运行的原型，或派生那些可以稍后再处理的探索性任务。这让工程师更容易暂停和恢复工作而不丢失上下文（context），尤其是在他们值班或会议很多的时候。
来自我们团队的轶事
如果我发现一个顺手就能修的 bug，我会派发一个 Codex 任务，而不是切换分支，等有空时再评审它的 PR。
后端工程师，ChatGPT API
我经常把 Slack 会话线程、Datadog 追踪、issue 等转发给 Codex，这样我就能专注于高优先级的工作。
API 工程师，基础设施可观测性（Infrastructure Observability）
试试用以下示例提示让 Codex 帮你保持心流：
生成一个重构这个服务并将其拆分为更小模块的计划。
先写出重试逻辑的桩并添加一个 TODO——我稍后再补充退避（backoff）逻辑。
总结这个文件，好让我明天能接着上次的地方继续。

使用场景 7
探索与构思
Codex 对开放式的工作也很有用，例如寻找替代方案或验证设计决策。你可以提示它给出解决问题的不同方式、探索不熟悉的模式，或对假设进行压力测试。这有助于揭示权衡（trade-off）、扩展设计选项，并让实现选择更加清晰。
它还被用来识别相关的 bug。给定一个已知的 issue 或已弃用的方法，Codex 可以识别代码中其他地方的相似模式，从而更容易发现回归或完成清理工作。
来自我们团队的轶事
Codex 帮我解决冷启动（cold-start）问题——我粘贴一份规格和文档，它就会搭建代码，或指出我遗漏了什么。
产品工程师，ChatGPT Desktop
修复一个 bug 后，我会问 Codex 类似 bug 可能潜伏在哪里，然后派发后续任务。
性能工程师，检索系统（Retrieval Systems）
试试用以下示例提示让 Codex 做探索与构思
如果系统是事件驱动而不是请求/响应式的，它会如何工作？
找出所有手工拼接 SQL 字符串、而不是使用我们查询构建器（query builder）的模块。
用更函数式的风格重写这段代码，避免可变状态（mutation）和副作用。

最佳实践
当 Codex 获得结构、上下文以及迭代空间时，它的表现最好。以下是 OpenAI 团队在日常工作中逐步养成的一些习惯，用以持续稳定地从中获取价值。
从 Ask 模式开始
对于大型改动，先用 Ask 模式让 Codex 给出一个实现计划，这个计划随后会成为你切换到 Code 模式时后续提示的输入。这种两步式流程能让 Codex 保持接地气，并帮助避免其输出中的错误。Codex 最擅长处理那些任务边界清晰、你或同事大约需要一小时完成、或需要几百行代码来实现的工作。随着模型不断改进，预计它能够承担的任务规模还会继续增大。
迭代改进 Codex 的开发环境
设置启动脚本、环境变量和网络访问能显著降低 Codex 的错误率。在运行任务时，留意那些可以在 Codex 环境配置中修正的构建错误。这可能需要几次迭代，但从长远来看能带来显著的效率提升。
像写 GitHub Issue 一样组织你的提示
当提示镜像了你在 PR 或 issue 中描述改动的方式时，Codex 的响应会更好。这意味着在相关时包含文件路径、组件名称、diff 以及文档片段。使用「按照[模块 X]里的做法来实现这个」这类模式进行提示，能改善结果。
把 Codex 任务队列当作轻量级待办列表使用
派发任务来记录相关的想法、部分完成的工作，或顺手要做的修复。不必急于一次性生成一个完整的 PR。Codex 很适合作为一个你可以稍后回来继续处理的暂存区。

最佳实践
使用 AGENTS.md 提供持久化上下文
维护一个 AGENTS.md 文件，帮助 Codex 在你的仓库中跨提示更高效地工作。这些文件通常包含命名规范、业务逻辑、已知的怪癖，或 Codex 仅凭代码无法推断出的依赖。要了解更多关于如何组织 AGENTS.md 文件，请参阅文档。
利用「Best of N」来改善输出
Best-of-N 功能让你能为单个任务同时生成多个响应，从而快速探索多种方案并选出最好的一个。对于更复杂的任务，你可以评审多次迭代，并组合不同响应中的部分内容，从而得到更强的结果。
展望未来
Codex 仍处于研究预览（research preview）阶段，但它已经在改变我们的开发方式，帮助我们更快地推进、写出更好的代码，并承担那些原本永远不会被优先处理的工作。
我们对前方的潜力感到兴奋——随着我们的模型越来越好、Codex 越来越深入地融入我们的工作流，我们期待用它解锁更强大的软件开发方式。我们将继续分享一路走来的所学所得。
